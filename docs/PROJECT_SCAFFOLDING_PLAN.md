# PIOS Project Scaffolding Plan

Status: Draft — Derived from Approved Foundation. This document defines how the repository and initial project structure will be organized before implementation begins: repository organization, initial areas, module placement, documentation placement, and the development starting point. It creates no repository file, no code, and no infrastructure; it is a plan for how those will later be organized.

This document is derived exclusively from [PROJECT_CONSTITUTION.md](PROJECT_CONSTITUTION.md), the ADR Foundation (through ADR-026), [SYSTEM_ARCHITECTURE.md](SYSTEM_ARCHITECTURE.md), [APPLICATION_ARCHITECTURE.md](APPLICATION_ARCHITECTURE.md), [API_SPECIFICATION.md](API_SPECIFICATION.md), [DATABASE_DESIGN.md](DATABASE_DESIGN.md), [MODULE_STRUCTURE.md](MODULE_STRUCTURE.md), [INTERFACE_CONTRACTS.md](INTERFACE_CONTRACTS.md), and [ENGINEERING_GUIDELINES.md](ENGINEERING_GUIDELINES.md), in that order of authority. It introduces no module, technology, or deployment decision beyond what these documents already establish.

---

## 1. Purpose

Scaffolding is defined before implementation so that the repository's physical shape reflects the architecture already approved — MODULE_STRUCTURE.md's eight modules, INTERFACE_CONTRACTS.md's boundaries, ADR-023 through ADR-026's technology and deployment decisions — before a single line of code exists to contradict it. Consistent with Documentation Driven Development (ADR-006) and Architecture First (ADR-001), the first code written should already have a home consistent with domain isolation (ADR-009), rather than a structure emerging ad hoc and needing correction after the fact.

## 2. Scaffolding Principles

- **Architecture Alignment.** The repository's physical organization mirrors the architecture already approved — one area per module (MODULE_STRUCTURE.md Section 3), consistent with ADR-001.
- **Module Isolation.** No shared code area exists between modules beyond what MODULE_STRUCTURE.md Section 4 already allows as uniform principles applied independently; no area represents shared business ownership.
- **Clear Ownership.** Every area of the repository has exactly one owning module or one non-module purpose (documentation, configuration), consistent with the Explicit Ownership principle in MODULE_STRUCTURE.md Section 2.
- **Documentation Proximity.** Documentation that governs a module remains discoverable from within it, without duplicating the authoritative copy already in `docs/`, consistent with the Repository Strategy already established in ADR-008.
- **Future Scalability.** The structure accommodates every module becoming its own independently deployable unit (ADR-026) without requiring a wholesale reorganization later.
- **Minimal Initial Complexity.** No area is scaffolded before it is needed; an area exists once a module's implementation actually begins, consistent with the No Premature Optimization principle in ENGINEERING_GUIDELINES.md Section 3.

## 3. Repository Organization

The following is a conceptual illustration of area names and their purpose, not a literal file listing to be generated by this document:

```
pios/
├── docs/                       Existing documentation (ADR-008; unchanged by this plan)
├── backend/                    Backend area (ADR-023: Kotlin, Spring Boot)
│   └── [one area per module — Section 4]
├── frontend/                   Frontend area (ADR-024: TypeScript, React / React Native)
│   └── [one area per experience — Section 5]
└── [repository-level configuration area]
```

- **Documentation.** Remains exactly where ADR-008 already placed it; this plan adds no new documentation area.
- **Backend area.** One conceptual sub-area per backend module (Section 4), consistent with ADR-023's one-independently-deployable-service-per-module decision.
- **Frontend area.** One conceptual sub-area per frontend experience (Section 5), consistent with ADR-024.
- **Module areas.** Every backend and frontend area is itself a module or experience area; none spans more than one.
- **Configuration areas.** Repository-level configuration only — for example, what governs the repository as a whole, not any module's own application configuration, which belongs within that module's own area once it exists.

## 4. Backend Structure

Each of the eight ratified modules (MODULE_STRUCTURE.md Section 3) has its own conceptual area within `backend/`. No class or package is defined here.

| Module | Ownership | Boundary | Responsibility |
| --- | --- | --- | --- |
| Order Management | Its own area; no other module's code lives there. | Crossed only through its declared interaction or published events (MODULE_STRUCTURE.md). | An order's lifecycle from submission through completion or cancellation. |
| Dispatch | Its own area. | Only Dispatch's own area determines or changes an assignment. | The assignment decision, exclusively. |
| Driver Management | Its own area. | Only its own area changes a driver's availability state. | A driver's standing, availability, and participation. |
| Passenger Experience | Its own area. | Only its own area owns passenger and corporate customer representation. | Passenger and corporate customer interaction with the platform. |
| Administration | Its own area. | Only its own area owns governance and standing information. | Overseeing and governing the ecosystem. |
| Analytics | Its own area. | Never contains the underlying information it derives insight from. | Derived, aggregate insight only. |
| Notifications | Its own area. | Never contains the underlying information that triggers a notification. | Informing participants. |
| Payments | Its own area. | Never contains external settlement information. | The platform's own payment record. |

Each area corresponds one-to-one with the module it represents; no backend area contains more than one module's responsibility, consistent with MODULE_STRUCTURE.md Section 2 (High Cohesion, Explicit Ownership).

## 5. Frontend Structure

Consistent with ADR-024, each frontend experience has its own conceptual area within `frontend/`. No UI component is defined here.

- **Passenger application area.** React Native (TypeScript), consuming Order Management and Passenger Experience per UC-001 and UC-002.
- **Driver application area.** React Native (TypeScript), consuming Driver Management and Dispatch per UC-003 through UC-006.
- **Corporate interface area.** React (TypeScript) web application, consuming Order Management through Passenger Experience's originating context per UC-009.
- **Administrator interface area.** React (TypeScript) web application, consuming Administration per UC-010; per ADR-024's Multi-Experience Consideration, this area also serves any operational need, since no independent Dispatcher/Operations capability is established beyond Administration.

## 6. Documentation Structure

The documentation structure already established (`docs/README.md`) is not changed by this plan:

- **Architecture documents.** SYSTEM_ARCHITECTURE.md, APPLICATION_ARCHITECTURE.md, API_SPECIFICATION.md, DATABASE_DESIGN.md, MODULE_STRUCTURE.md, INTERFACE_CONTRACTS.md, and the data model documents remain in `docs/`.
- **ADR documents.** Remain in `docs/ADR/`, following the naming and status conventions already established.
- **Engineering documents.** ENGINEERING_GUIDELINES.md and this plan remain in `docs/`.
- **Product documents.** PRODUCT_FOUNDATION.md, DOMAIN_MODEL.md, EVENT_CATALOG.md, and USE_CASE_CATALOG.md remain in `docs/`.

Code areas (Sections 4–5) reference this documentation; they never duplicate it.

## 7. Development Sequence

No code is written as part of defining this sequence.

1. **Foundation.** The repository areas themselves (Section 3) and the shared engineering conventions (ENGINEERING_GUIDELINES.md) are established before any module-specific work begins.
2. **Core domain modules.** Consistent with the dependency graph already established in INTERFACE_CONTRACTS.md Section 3, Driver Management and Passenger Experience — which depend on no other module — are the natural starting point, followed by Dispatch (depends on Driver Management) and Order Management (depends on Passenger Experience and Dispatch); Administration proceeds independently at any point, since it is self-contained.
3. **Interfaces.** The commands, queries, and events named in INTERFACE_CONTRACTS.md are implemented as each module reaches the point of exposing them, not as a separate, later phase across every module at once.
4. **Data.** Each module's own persistence (DATABASE_DESIGN.md; ADR-025) is implemented alongside that module, never as a shared phase, consistent with ADR-005's exclusive ownership.
5. **User experiences.** Frontend areas (Section 5) begin once the backend modules they depend on expose the contracts they need — the Passenger and Driver applications require Order Management, Dispatch, Driver Management, and Passenger Experience; the Administrator interface requires Administration.

Analytics, Notifications, and Payments — none currently attributed a driving use case (USE_CASE_CATALOG.md, Areas Not Catalogued) — are not placed in this sequence ahead of the modules that would give them something to consume or a reason to be invoked; they proceed once that grounding exists.

## 8. Environment Preparation Principles

No tool is named here. Environment preparation means ensuring every engineer, human or AI, can build and run a single module's area in isolation, consistent with that module's independent deployability (ADR-026), before needing to work across modules. It means the Development Workflow already established in ENGINEERING_GUIDELINES.md Section 4 — planning, implementation, review, validation, documentation update — can actually be followed without a missing prerequisite. It does not mean selecting or configuring any specific tool, which remains a later, implementation-level decision outside this plan's scope.

## 9. Repository Evolution

The repository structure evolves the same way the architecture it reflects does — only through a decision that explicitly supersedes the one that established it, consistent with ADR-015. Because ADR-026 already commits every module to independent deployability as a release-process property, the structure in Section 3 must be able to support each module's area becoming its own independently released artifact without a wholesale reorganization, consistent with the Future Scalability principle in Section 2. If a module's own area later needs to become a fully separate repository rather than an area within one repository, that is a decision requiring an ADR that supersedes ADR-008 (Repository Strategy), not something this plan pre-decides.

## 10. First Implementation Milestone

The first implementation milestone's purpose is to prove the scaffolding itself: that the areas defined in Section 3 exist, that a single module's area can be built and run in isolation consistent with ADR-026, and that the Development Workflow in ENGINEERING_GUIDELINES.md Section 4 can be followed end to end for that one module — before any business capability is implemented. Its success criterion is that the scaffolding works, not that a use case (USE_CASE_CATALOG.md) is fulfilled; use case implementation follows in later milestones, once the scaffolding this plan describes is confirmed to hold.
