## 1. Что это и для кого

**Проектная линза, заданная Product Owner дословно:**

> «Не проектируй Dashboard как внутренний инструмент разработчика. Проектируй его как пульт управления владельца бизнеса, который не умеет программировать.»

Это правило применяется ко всему ниже — к экранам, к текстам ошибок и к формулировкам самих ADR.

**Один вопрос, на который экран отвечает за 5 секунд:** «Работает ли сейчас мой бизнес?»

**Кто пользуется:** один человек — владелец платформы. Не диспетчер, не разработчик, не администратор. Ролей нет и не будет (ADR-044, Decision 6).

**Устройства:** отзывчивый веб, mobile-first. iPhone, Android, десктоп. Нативного приложения нет и не будет в этом MVP.

## 2. Границы MVP

**Входит:** наблюдение за состоянием системы; счётчики за сегодня; лента событий человеческим языком; понятное описание проблемы, когда она есть; кнопка «Подготовить отчёт»; вход по логину и паролю.

**Не входит — ни в каком виде, ни в какой итерации этого MVP:**

| Исключено | Почему |
|---|---|
| Управление водителями, пассажирами, заказами | Решение Product Owner: наблюдение, не управление |
| Редактирование базы, SQL | То же |
| Запуск/остановка/перезапуск сервисов | То же. Плюс ADR-043 Decision 5: поверхность только на чтение по своей природе |
| Настройки, роли, права | ADR-044 Decision 6 |
| Деньги: выручка, средний чек, суммы | ADR-042 R4.3 — запрет прямой и не обходится продуктовым решением о дашборде |
| Бизнес-аналитика, графики, отчёты, история за период | `PIOS_PILOT_OPERATION_PROTOCOL.md` Раздел 6 остаётся в силе для всего, кроме счётчиков за текущий день |
| Push-уведомления | Отложены Product Owner. Архитектура их не запрещает — см. Раздел 14 |
| Аутентификация водителей и пассажиров | ADR-044 Decision 11 — отдельная, большая работа |

## 3. Архитектура одной картинкой

```
                     iPhone / Android / десктоп
                    +---------------------------+
                    |  Owner Control Center     |
                    |  (React, страница в PWA)  |
                    +-------------+-------------+
                                  |
                   один origin (Cloudflare Tunnel -> vite preview proxy)
                                  |
     +----------+----------+------+-----+----------+-----------+
     |          |          |            |          |           |
  8081       8082       8083         8084       8086        (8085)
 driver-   passenger-   order-      dispatch   identity    network-
 mgmt      experience   mgmt                               management
     |          |          |            |          |           |
   своя БД    своя БД    своя БД     своя БД    своя БД     НЕ УЧАСТВУЕТ
```

Ключевое свойство: **горизонтальных стрелок между сервисами нет.** Ни один модуль не знает о существовании другого. Всё сведение данных происходит в браузере владельца и нигде не сохраняется (ADR-043, Decision 1).

Нового модуля нет. Нового сервиса нет. Агрегирующего эндпоинта нет.

## 4. Аутентификация: как она устроена и как выглядит

Полное архитектурное обоснование — ADR-044. Здесь — то, что видит владелец, и то, что нужно разработчику.

### 4.1. Механизм в четырёх предложениях

Логин и пароль хранятся не в базе, а в настройках развёртывания (хеш пароля, не сам пароль). Владелец вводит их один раз при входе; введённые данные остаются в памяти вкладки и прикладываются к каждому запросу к `/v1/health`. Каждый сервис проверяет их сам, ни у кого ничего не спрашивая и ничего не выдавая. Отдельного эндпоинта входа нет — вход и есть первый успешный запрос к `/v1/health`.

> **Изменено 2026-08-02 по итогам критического разбора перед ратификацией.** В первой редакции здесь был подписанный пропуск на 12 часов и два эндпоинта `/v1/owner/session`. Пропуск убран: он создавал единственное место, где один модуль доверял выпуску другого, делал отзыв доступа невозможным в течение 12 часов и был единственной самописной криптографией в проекте. Полное обоснование — ADR-044, раздел «Revision 2026-08-02».

### 4.2. Где в маршрутах сидит вход

```
/                       -> DriverHome            (без входа, как сегодня)
/i/:driverCode          -> PassengerLanding      (без входа, как сегодня)
/i/:driverCode/request  -> RideRequest           (без входа, как сегодня)
/coordinator            -> Coordinator           (без входа, как сегодня)
/network-test           -> NetworkTest           (без входа, как сегодня)

/owner                  -> если пропуска нет  -> экран входа
                           если пропуск есть  -> Owner Control Center
```

Ни один существующий маршрут не меняется. Ни один экран водителя или пассажира не получает вход.

### 4.3. Что видит владелец в трёх случаях отказа

| Ситуация | Что на экране | Чего на экране нет |
|---|---|---|
| Неверный пароль | «Неверный логин или пароль» | 401, Unauthorized, слова «токен» |
| Вкладка закрыта или долго простаивала | «Войдите ещё раз» — форма входа с сохранённым логином | 403, «сессия», «expired», «токен» |
| Не удаётся проверить пароль (сервис не отвечает) | «Сейчас не удаётся проверить пароль. Попробуйте через минуту» | Технические детали |

### 4.4. Отдельное правило, важное для честности экрана

Если пропуск есть, но какой-то сервис отвечает «не пущу» (например, из-за расхождения настроек), это **не** проблема бизнеса и **не** повод показывать красный экран «PIOS требует внимания». Показывается отдельное, третье состояние:

```
|   Не удаётся получить часть данных.        |
|   Нужна проверка настроек.                 |
|                                            |
|   Это не сбой в работе с заказами.         |
```

Смешивать ошибку доступа с производственным сбоем нельзя: владелец начнёт искать проблему у водителей там, где её нет.

## 5. Экраны

Все макеты — вертикальный экран телефона. На десктопе те же карточки в одну колонку по центру, шире.

### 5.1. Вход

```
+-------------------------------+
|                               |
|            PIOS               |
|                               |
|      Пульт владельца          |
|                               |
|                               |
|   Логин                       |
|   +-----------------------+   |
|   |                       |   |
|   +-----------------------+   |
|                               |
|   Пароль                      |
|   +-----------------------+   |
|   |                       |   |
|   +-----------------------+   |
|                               |
|   +-----------------------+   |
|   |        Войти          |   |
|   +-----------------------+   |
|                               |
|   Неверный логин или пароль   |   <- только после неудачной попытки
|                               |
+-------------------------------+
```

Ничего больше. Нет «забыли пароль» (некуда вести), нет регистрации (владелец один), нет упоминания сервисов.

### 5.2. Главный экран — зелёное состояние

+-------------------------------+
|                               |
|          ( ● )                |

|                               |

|                               |

|                               |
+-------------------------------+
| СЕГОДНЯ                       |
|                               |
|   Водителей всего        3    |
|   На линии сейчас        2    |
|                               |
|   Заказов создано        7    |
|     выполнено            5    |
|     в работе             1    |
|     отменено             1    |
|                               |
+-------------------------------+
| ЧТО ПРОИСХОДИЛО               |
|                               |
|  20:44   Сергей —             |
|          новый водитель       |
|  20:28   Артур завершил       |

### 5.3. Главный экран — красное состояние

Верхняя карточка заменяется целиком. Карточки «Сегодня» и лента остаются ниже, с пометкой о том, что данные могут быть неполными.

```
+-------------------------------+
|  PIOS                   20:47 |
+-------------------------------+
|                               |
|          ( ● )                |
|      красный круг             |
|                               |
|    PIOS требует внимания      |
|                               |
|   Новые пассажиры сейчас      |
|   не могут оформить заказ.    |
|                               |
|   Началось в 20:31            |
|   (16 минут назад)            |
|                               |
|   Водители, которые уже       |
|   в поездке, могут её         |
|   завершить.                  |
|                               |
+-------------------------------+
|   [ Подготовить отчёт ]       |
+-------------------------------+
| СЕГОДНЯ                       |
|   Данные могли устареть       |
|   ...                         |
+-------------------------------+
```

Если проблем несколько, показываются все, сверху вниз, каждая своей строкой — без сортировки по «важности», потому что критерия важности у нас нет и выдумывать его нельзя.

### 5.4. Жёлтое состояние — работает, но с оговоркой

Отдельное состояние для случая, когда все сервисы отвечают, но у кого-то накопилась очередь неотправленных событий.

```
|          ( ● )                |
|       жёлтый круг             |
|                               |
|   PIOS работает с оговоркой   |
|                               |
|   Заказы принимаются, но      |
|   доходят до водителей        |
|   с задержкой.                |
|                               |
|   Задержка около 3 минут,     |
|   началось в 20:31.           |
```

Это тот самый сигнал, ради которого в `/v1/health` есть возраст самой старой неотправленной записи. Без него застрявшая очередь выглядела бы как «всё зелено», хотя водители заявок не получают.

### 5.5. Экран без данных

```
|          ( ● )                |
|       серый круг              |
|                               |
|   Проверяю...                 |
|                               |
```

и, если за 10 секунд не удалось получить ничего вообще:

```
|   Не удаётся связаться        |
|   с PIOS.                     |
|                               |
|   Проверьте интернет на       |
|   этом устройстве.            |
|                               |
|   [ Попробовать снова ]       |
```

Важное различие: «мой телефон без сети» и «PIOS лежит» выглядят по-разному. Если не отвечает вообще ничего, включая статику самой страницы, вероятнее первое.

### 5.6. Что выдаёт кнопка «Подготовить отчёт»

Текст копируется в буфер обмена одним нажатием, чтобы владелец вставил его в переписку с Claude.

## 6. Язык интерфейса

Обязательная таблица соответствий. Разработчик реализует именно её, а не придумывает формулировки.

| Что не отвечает | Что показывается владельцу |

Запрещены на экране (не в отчёте) без исключений: HTTP, код ответа, stack trace, RabbitMQ, очередь как техническое слово, TimeoutException, SQLException, JVM, Spring, PostgreSQL, outbox, порт, endpoint, API, токен, сессия.

Проверочный вопрос к любой строке на экране: **поймёт ли её человек, который никогда не открывал терминал?** Если нет — строка неверна.

## 7. API

### 7.1. Новых эндпоинтов входа нет

Отдельного API для входа не существует. Форма входа отправляет логин и пароль сразу на `GET /v1/health/<имя-модуля>` (любого из пяти — путь каждого модуля свой, `PILOT_INFRASTRUCTURE_ROUTING_DECISION.md` Variant A):

- ответ **200** — данные верны, пульт открывается;
- ответ **401** — данные неверны, показывается «Неверный логин или пароль»;
- **ответа нет вообще** — показывается «Сейчас не удаётся проверить пароль», а не «неверный пароль». Это различие уже умеет делать `apiClient.ts` (строки 61–74): ответ с кодом приходит как `ApiError`, сетевой сбой — нет.

Выход — на стороне браузера: логин и пароль удаляются из памяти вкладки. Серверного эндпоинта нет и не нужно: сервер не хранит никакого состояния сессии (ADR-044, Decision 7).

Отзыв доступа при компрометации: сменить `pios.owner.password-hash` и перезапустить сервисы — действует немедленно и полностью.

### 7.2. Новое: состояние службы — единственный новый эндпоинт этого MVP

**`GET /v1/health/<имя-модуля>`** — на всех пяти сервисах, каждый под своим путём (`/v1/health/driver-management`, `/v1/health/passenger-experience`, `/v1/health/order-management`, `/v1/health/dispatch`, `/v1/health/identity`). Требует `Authorization: Basic base64(логин:пароль)`; без него или с неверными данными — 401. Суффикс с именем модуля — деталь маршрутизации, а не часть контракта ADR-043 Decision 2: пять модулей иначе отвечали бы на один и тот же путь, что единый прокси пилотной инфраструктуры не может различить (`PILOT_INFRASTRUCTURE_ROUTING_DECISION.md` Variant A, утверждено Product Owner 2026-08-03).

Три обязательных требования к реализации 401 на этом эндпоинте:

- **заголовок `WWW-Authenticate` не отправляется.** Иначе браузер откроет собственное системное окно ввода пароля вместо нашего экрана входа — и заговорит с владельцем своими словами, что прямо запрещено Разделом 11 Product Decision;
- логин не может содержать двоеточие;
- ответ не различает «нет такого логина» и «неверный пароль», и ни то ни другое не пишется в лог.

```json
{
  "module": "dispatch",
  "status": "UP",
  "database": "UP",
  "outbox": { "pending": 14, "oldestPendingAgeSeconds": 372 },
  "checkedAt": "2026-08-02T15:47:03Z"
}
```

`outbox` отсутствует у `passenger-experience` и `identity` — у них нет outbox-таблицы. Модуль сообщает только о себе и никогда о других (ADR-043, Decision 2).

**Обязательное ограничение реализации.** Показатели очереди считаются одним агрегирующим запросом (`SELECT count(*), min(created_at) ... WHERE published_at IS NULL`), новым методом на уже существующем интерфейсе `OutboxRepository`. Существующий `findUnpublished()` для этого использовать **нельзя**: он загружает в память все неотправленные записи целиком, вместе с payload, — то есть проверка состояния становилась бы тем тяжелее, чем больше очередь, и хуже всего работала бы ровно в той ситуации, ради обнаружения которой существует. Переиспользуется место, а не метод.

`status: "DOWN"` возвращается с кодом 503, когда собственная база не отвечает — процесс жив, но работать не может. Это отдельный случай от «нет ответа вообще», и на экране он звучит иначе.

### 7.3. Расширяется: существующие ответы получают время

Все поля — необязательные, добавляются в конец, старые клиенты не ломаются.

`GET /v1/drivers` и `GET /v1/drivers/{id}`:
```json
{ "driverId": "...", "availability": "AVAILABLE", "displayName": "Артур",
  "registeredAt": "2026-08-02T15:44:10Z" }
```

`GET /v1/proposals?orderId=...` / `?driverId=...`:
```json
{ "proposalId": "...", "orderId": "...", "driverId": "...", "status": "ACCEPTED",
  "statedPrice": "...", "createdAt": "...", "respondedAt": "..." }
```
`statedPrice` уже присутствует сегодня. Клиент обязан его **отбросить при получении** — не показывать, не складывать, не класть в отчёт (ADR-043, Decision 6).

`GET /v1/assignments?orderId=...`:
```json
{ "assignmentId": "...", "orderId": "...", "driverId": "...", "status": "COMPLETED",
  "statusChangedAt": "...", "arrivedAt": "...", "startedAt": "...", "completedAt": "..." }
```
`statusChangedAt` остаётся. Заменять его нельзя — это изменило бы модель, ратифицированную ADR-040, и потребовало бы своего ADR.

### 7.4. Не меняется ничего больше

Контракты `GET /v1/orders`, `POST /v1/orders`, `POST /v1/drivers`, `POST /v1/drivers/{id}/availability`, `POST /v1/proposals` и его accept/decline/lapse, `POST /v1/assignments` и его arrive/start/complete, `POST /v1/connections`, `POST /v1/identities` — без изменений. Обязательность параметров `orderId`/`driverId` сохраняется намеренно (ADR-043, Decision 3): дашборд делает несколько маленьких запросов вместо того, чтобы открыть всем возможность выгрузить всё.

### 7.5. Как страница опрашивает систему

Раз в 15 секунд, последовательно, с отменой при уходе со страницы:

1. `GET /v1/health` × 5 — состояние и очереди.
2. `GET /v1/orders` — заказы, счётчики, лента заказов.
3. `GET /v1/drivers` — водители, счётчики, лента регистраций.
4. `GET /v1/proposals?driverId=…` — по каждому водителю.
5. `GET /v1/assignments?orderId=…` — по каждому сегодняшнему заказу, у которого есть принятое предложение.

Порядок важен: п. 1 определяет цвет главной карточки и должен успеть отработать раньше остального. Если п. 2–5 не отвечают, показываются последние успешно полученные данные с честной пометкой о времени.

## 8. Изменения в данных

Три миграции, все колонки nullable, без DEFAULT, точный прецедент — `V6__add_optional_order_destination.sql`, `V7__add_passenger_name_and_created_at.sql`, `V5__assignment_ride_lifecycle.sql`.

| Модуль | Миграция | Что добавляет |
|---|---|---|
| driver-management | `V4__add_driver_created_at.sql` | `drivers.created_at TIMESTAMPTZ NULL` |
| dispatch | `V7__proposal_timestamps.sql` | `proposals.created_at`, `proposals.responded_at` |
| dispatch | `V8__assignment_transition_timestamps.sql` | `assignments.arrived_at`, `started_at`, `completed_at` |

Ничего не удаляется и не переименовывается. `assignments.status_changed_at` остаётся на месте.

**Что нужно сказать владельцу заранее, чтобы это не стало сюрпризом на экране:** все записи, созданные до этих миграций — в том числе регистрация Артура и все заказы, уже прошедшие через систему, — навсегда останутся без времени. Лента будет полной только с момента поставки. Записи без времени в ленту не попадают вообще; выдумывать им время нельзя.

Backend (точечно): три миграции, три расширения ответов, запись новых временных меток в местах, где статус уже меняется.
Frontend: экран входа; хранение и продление пропуска; страница Control Center; опрос; таблица человеческих формулировок; сборка отчёта.

## 11. План работ

Порядок не произвольный. Обоснование каждого решения о порядке — в скобках.

**Этап 0 — документы. Без него не начинается ничего.**
1. `docs/PRODUCT_DECISION_OWNER_CONTROL_CENTER.md` — то, что требует `PIOS_PILOT_OPERATION_PROTOCOL.md` Раздел 6.
2. Ратификация ADR-043 и ADR-044 Product Owner.
3. `API_SPECIFICATION.md` и `INTERFACE_CONTRACTS.md` — описание `/v1/owner/session` и `/v1/health` до их реализации (ADR-006, `CLAUDE.md`).

**Этап 1 — аутентификация. Раньше наблюдения, не позже.**
4. Проверка логина и пароля в одном модуле, с тестами: верные данные, неверный пароль, отсутствующий заголовок, отсутствие `WWW-Authenticate` в ответе 401, ограничение числа неудачных попыток.
5. То же самое в остальных четырёх модулях.
6. Экран входа, хранение данных в памяти вкладки, все три сценария отказа из п. 4.3.

Почему аутентификация первая, а не после: ADR-011 требует, чтобы безопасность была свойством, заложенным при проектировании границы, «а не добавленным после». Эндпоинты `/v1/health` должны родиться закрытыми. Если порядок обратный, они какое-то время живут открытыми, и «закроем потом» превращается в привычку. Плюс практическое: если сроки поедут, доделанным должен оказаться замок, а не третий счётчик на карточке.

**Этап 2 — состояние служб. Без изменений схемы, поэтому разворачивается безопасно.**
7. `GET /v1/health` в пяти модулях, закрытый пропуском с самого начала.
8. Чтение собственного outbox в трёх модулях, у которых он есть.
9. Маршруты для новых путей в прокси + правка документа об инфраструктуре — решено `PILOT_INFRASTRUCTURE_ROUTING_DECISION.md` (Variant A, утверждено Product Owner 2026-08-03): `/v1/health/<имя-модуля>`, пять строк в `preview.proxy`, без переписывания.

**Этап 3 — временные метки. Единственный этап, который трогает базы.**
10. Три миграции.
11. Запись меток в существующих местах смены статуса.
12. Новые поля в ответах.

Выполняется вне рабочей смены Артура, отдельным развёртыванием, с проверкой экранов водителя и пассажира сразу после.

**Этап 4 — экран.**
13. Главная карточка: зелёный / жёлтый / красный / серый, с таблицей формулировок из Раздела 6.
14. Карточка «Сегодня».
15. Лента событий.
16. Кнопка «Подготовить отчёт».
17. Проверка на реальном iPhone через пилотный адрес, включая установку на домашний экран.

**Этап 5 — QA.** Сквозные сценарии: вход, неверный пароль, истёкший пропуск, погашенный сервис (по одному из пяти), застрявший outbox, полный цикл заказа с проверкой ленты, регрессия экранов водителя и пассажира.

## 12. Оценка трудоёмкости

Предыдущая оценка Оптимального уровня без аутентификации была 3–5 рабочих дней. С аутентификацией:

| Работа | Оценка |
|---|---|
| Документы (Этап 0) | 0,5 дня |
| Аутентификация backend, пять модулей (Этап 1, п. 4–5) | 0,75 дня |
| Аутентификация frontend (Этап 1, п. 6) | 0,25 дня |
| `/v1/health` и очереди (Этап 2) | 1 день |
| Миграции, метки, поля (Этап 3) | 1 день |
| Экран Control Center (Этап 4) | 2 дня |
| QA (Этап 5) | 1 день |
| **Итого** | **6,5 дня, реалистично 6–7 рабочих дней** |

Оценка снижена с 7–9 дней после критического разбора 2026-08-02: вместе с подписанным пропуском исчезли формат токена, срок его жизни, проверка подписи, два эндпоинта входа и их тесты — в пяти модулях каждый.

**Где оценка может поехать сильнее всего.** Не в экране и не в миграциях — в пятикратном повторении настроек. Три значения (`pios.owner.username`, `pios.owner.password-hash`, `pios.owner.password-salt`) должны совпадать во всех пяти развёртываниях, и расхождение проявится не как понятная ошибка, а как «часть данных не приходит». Именно поэтому в п. 4.4 предусмотрено отдельное состояние экрана для такого случая — чтобы этот сбой не выглядел как производственная авария.

## 13. Риски

| Риск | Насколько реален | Что делаем |
|---|---|---|
| Изменение схемы во время живой работы Артура | Средний | Этап 3 отдельным развёртыванием вне смены; все колонки nullable; регрессия экранов сразу после |
| Расхождение настроек между пятью модулями | Высокий | Отдельное состояние экрана (п. 4.4); проверка всех пяти при развёртывании |
| Браузер откроет своё системное окно ввода пароля вместо нашего экрана | Средний, если забыть про деталь | Ответ 401 не содержит `WWW-Authenticate` — отдельный обязательный тест |
| Проверка состояния сама становится нагрузкой при большой очереди | Был реальным в первой редакции | Агрегирующий запрос вместо `findUnpublished()` (Раздел 7.2) |
| Часовые пояса: «сегодня» по времени телефона против UTC в данных | Средний | Явно зафиксировать пояс на экране и в отчёте; проверить поведение после полуночи |
| Утечка пароля владельца | Низкий | Отзыв немедленный: смена `pios.owner.password-hash` и перезапуск (ADR-044, Decision 7). Пароль генерируется для развёртывания, не придумывается |
| Отсутствие TLS в каком-то развёртывании | Низкий | Записать как обязательное условие в документе об инфраструктуре (ADR-044, Decision 9) |
| Владелец решит, что «PIOS теперь защищён» | Реальный и человеческий | Сказать прямо: закрыт пульт, а не платформа. Данные заказов остаются публичными, как и были |

## 14. Что осознанно не входит

**Push-уведомления.** Отложены решением Product Owner. Архитектура их не перекрывает и не требует переделки: будущий уведомитель — это процесс, который опрашивает те же самые `GET /v1/health` и те же самые списки, а `/v1/health` спроектирован так, что уже содержит всё нужное для решения «слать или не слать». Telegram как вероятный следующий шаг рассматривается отдельно после этого MVP. Важное предупреждение на будущее: такой уведомитель — это новый постоянно работающий компонент, и он не может быть добавлен как деталь реализации этого MVP; ему потребуется своё решение, а если он оформится в модуль — ратификация нового bounded context (`MODULE_STRUCTURE.md` Раздел 8).

**Контекст Operations, история инцидентов, сквозная трассировка одного заказа через модули.** Не строятся (ADR-043, Decision 8). Долг ADR-012 по сквозной трассировке этим MVP не закрывается и не изображается закрытым.

**Аутентификация водителей и пассажиров.** Вне объёма (ADR-044, Decision 11).

**Деньги в любом виде.** ADR-042 R4.3.
