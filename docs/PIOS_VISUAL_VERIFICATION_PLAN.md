## 6. Safety considerations

- **Localhost-only by construction, not by special configuration.** A Playwright script (or the Playwright MCP server) only ever navigates to whatever URL is passed to it — this plan's own recommendation (Section 8) is to always pass a literal `http://127.0.0.1:<port>` URL, never a variable or user-suppliable one, so there is no path by which this capability could reach anything beyond the local dev server unless the script itself were changed to do so.
- **No production exposure.** Nothing in this plan touches the deployed/production frontend, the `pios-frontend` WinSW service, or any `https://home-pc.tail385153.ts.net/...` address — only the local Vite dev server, started and stopped within a single task.
- **No new runtime dependency for the PIOS application itself.** Whether using the already-installed Python Playwright (Section 2) or eventually installing the official `playwright` MCP plugin (Section 4), neither writes anything to `frontend/package.json`, `frontend/package-lock.json`, or `frontend/node_modules` — the plugin's MCP server runs as a wholly separate `npx`-spawned process, and the Python route uses a global, non-project Python environment.
- **Plugin install writes only to Claude Code's own project config**, not application source — confirmed via `claude plugin install -s project`'s own documented behavior (Section 4); this is a Claude-Code-specific manifest entry, not a change to anything the PIOS application ships or runs.
- **Dev-server lifecycle discipline**: any dev server started for verification must be explicitly stopped afterward (demonstrated in Section 10) — never left running unattended across tasks, consistent with this session's own established practice around every other service in this repository.

## 10. Acceptance test

**This test was actually performed in this task, not merely defined — because the task's own instructions explicitly permitted starting the dev server to verify an existing capability, using an existing safe command.** Result: it passed, on the first attempt, using only already-present tooling.

**What was done, in order:**
1. Confirmed port 5173 was free.
2. Started the dev server with the plain default (`npm run dev`) — it started, but the app was **unreachable** by any HTTP client (`curl`, PowerShell `Invoke-WebRequest`), including from the same machine. Root cause found: Vite's default `localhost` binding resolved to `::1` (IPv6 loopback) on this machine, and — confirmed independently via `Test-NetConnection -ComputerName '::1' -Port 5173`, which returned `TcpTestSucceeded: False` — **this machine's IPv6 loopback does not accept TCP connections at all**, a genuine, reproducible environment quirk, not a fluke of how the process was started.
3. Restarted with `npm run dev -- --host 127.0.0.1`, forcing IPv4 binding — immediately reachable (`curl` → `HTTP 200`).
4. Ran a 10-line Python script (Section 9, Step 3) using the already-installed Playwright package and already-downloaded Chromium — navigated to `http://127.0.0.1:5173/` (the `DriverHome` onboarding route) and saved a screenshot.
5. Used the `Read` tool on the resulting PNG — **the actual rendered page was visible**: a dark header reading "PIOS", a "Добро пожаловать!" heading, two informational cards, and a blue pill-shaped "Начать" button — this is real DOM-rendered output (correct Russian-language copy, correct component layout, correct fonts/colors as actually computed by the browser), not an HTTP status code or raw HTML source.
6. **A concrete visual observation was made from that screenshot**: the header bar ("PIOS", dark background, bold white centered text, generous vertical padding) reads as a prominent, branded app-bar — in tension with [PIOS_TAXI_DESIGN_BRIEF.md](PIOS_TAXI_DESIGN_BRIEF.md) Section 2's own Principle 1 ("PIOS's own mark stays small... never larger than the page's own identity element") and [PIOS_DESIGN_SYSTEM.md](PIOS_DESIGN_SYSTEM.md) Section 2's translation of it (the `Header` rule: "PIOS mark never styled larger/bolder than the page's own `DriverIdentity`"). This particular screen has no driver identity displayed yet (it is the pre-login welcome screen), so the rule isn't strictly violated here — but the header's own visual weight is exactly the kind of thing this brief-vs-implementation check is *for*, and it would be a legitimate first item on a design-system implementation punch list once a driver identity is present elsewhere on the same screen hierarchy for comparison.
7. Stopped the dev server (`Stop-Process` against the port's owning PID) — confirmed port 5173 free again afterward.

**This proves, concretely, not hypothetically:**
- Claude *can* access a local PIOS page (step 3/4).
- Claude *can* observe the actual rendered UI, not just an HTTP response (step 4/5 — real layout, real Russian-language text, real component styling, all only visible because the browser actually executed and rendered the page).
- Claude *can* capture and inspect a screenshot inline in the conversation (step 5).
- Claude *can* use that observation to identify a concrete, specific, brief-traceable visual issue (step 6) — not a generic "looks fine" response.

**Distinction this test specifically establishes**: HTTP reachability (`curl` returning `200`) and actual rendered-UI inspection are different capabilities that failed and succeeded at *different* points in this exact test — `curl` confirmed the server was serving *something*, but only the Playwright screenshot revealed what the page actually *looked like*. A future task relying on `curl`/HTTP-status checks alone would never have caught the header-weight observation in step 6, and would not have caught the broken-IPv6-loopback issue either, since Vite's own log claimed "ready" throughout — reachability had to be independently verified before rendering could even be attempted.
