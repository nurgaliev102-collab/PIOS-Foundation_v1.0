# ADR-063: Trip as a New Dispatch-Owned Aggregate, Distinct from Assignment

## Status

**Accepted, after correction.**

**Decision Date:** 2026-09-03.

**Basis (first correction, Task 10B).** The Trip-creation trigger originally read "at the moment an Assignment is accepted," which `docs/PIOS_TAXI_IMPLEMENTATION_READINESS_REVIEW.md` Section 2.2 found could be misread as, or implemented against, `Assignment.status == ACCEPTED` — a field that `ADR-040` Decision item 2 already documents may never actually be reached in the one real code path that creates an Assignment today. Corrected to name the `AssignmentAccepted` event/outcome explicitly as the trigger, never the mutable status field. With that correction applied, the decision is internally consistent with `ADR-040` (module-level holding: ride-progress stays in Dispatch, unaffected — Section 2.1 of the same review) and with `ADR-041`/`ADR-043` (unaffected in substance). Accepted per explicit Human Architect / Product Owner direction (Task 10B), consistent with `ADR-007`.

**Basis (second correction, Task 11A, 2026-09-03) — the first correction was itself incomplete.** Task 11's own mandatory pre-implementation call-graph inspection found that the first correction fixed the wrong half of the problem: it correctly rejected the mutable `Assignment.status` field as the trigger, but incorrectly assumed the `AssignmentAccepted` **event/outcome itself** is still produced by the live Proposal-acceptance path "even though the status field lags." Direct verification of the actual call graph (not the field, the constructor call) shows it is not: `AssignmentAccepted` is constructed in exactly one place (`Assignment.accept()`), `Assignment.accept()` is called in exactly one production method (`DispatchAssignmentApplicationService.acceptAssignment`), and that method is invoked by **no controller anywhere in the codebase** — `AssignmentController` exposes `assignOrder`, `listAssignments`, `/arrive`, `/start`, `/complete`, and no `/accept` endpoint. Both real production paths that create an Assignment (`ProposalAssignmentOrchestrationService.acceptProposal`, on driver acceptance of a Proposal; `AssignmentController.assignOrder`, on Coordinator manual assignment) call `Assignment.create()`, never `.accept()` — publishing `OrderAssigned`, never `AssignmentAccepted`. **`AssignmentAccepted` is therefore not produced by any live production path today.** Full evidence trail: `docs/PIOS_TAXI_TASK_11_TRIP_FOUNDATION_REPORT.md` (Task 11's own STOP report) and `docs/PIOS_TAXI_TASK_11A_ARCHITECTURE_CORRECTION.md`.

**Corrected trigger (Task 11A): `OrderAssigned`, not `AssignmentAccepted`.** See the Decision section's own updated "Trip's creation trigger" bullet below for the full, re-derived rationale. This does not reopen the first correction's own reasoning (the mutable status field remains the wrong trigger, for the same reasons as before) — it replaces the *event name* that correction settled on with the one actually verified to fire.

**Explicitly not done, per Task 11A's own instruction:** `AssignmentAccepted` was not wired into any live production path to make the original trigger technically true, no fake acceptance step was added, and the meaning of `AssignmentAccepted` (still a real, correctly-modeled, correctly-outbox-capable event — simply not currently reachable in production) was not changed.

**What acceptance authorizes and does not authorize, restated for clarity.** Accepted as an **architectural contract** — the Order/Assignment/Trip boundary, the Dispatch-internal (not a new module) placement, and the (now twice-corrected) trigger are now ratified. **Not authorized by this acceptance**: any code, migration, or event rename (none exists yet); the `Assignment*` → `Trip*` event rename itself remains unimplemented, gated on the dual-publish migration window this ADR's own Consequences section describes; mid-Trip cancellation remains explicitly unresolved (see "Relationship to other concepts," Cancellation, below); the separate, pre-existing Order Management event-consumption gap this correction surfaced (Section below, "Consequences") remains unresolved and explicitly out of this ADR's own scope.

**Implementation note (Task 12, Trip Ride-Progress Convergence, 2026-09-03) — the dual-publish window is now live; one clause of this ADR's own Decision section was deliberately not executed as written.** Trip now validates, persists, and publishes every ride-progress transition (`DispatchAssignmentApplicationService.arriveAssignment`/`startAssignment`/`completeAssignment`), and both the legacy `Assignment*` outbox event and the new `Trip*` one are published for each transition, exactly as this ADR's own Consequences section anticipated. **Deviation, stated plainly:** the Decision section below says `Assignment.arrive()`/`start()`/`complete()` "are removed from Assignment and relocated to Trip." They were not removed. Task 12's own governing instruction (Phase 3) is more specific than this ADR's own text and was treated as controlling for the implementation: *"Do NOT delete existing Assignment fields or endpoints merely because Trip now exists. Only remove old behavior after proving that no active consumer depends on it."* That proof does not exist — `AssignmentController.arrive/start/complete` are live, called today by `DriverHome.tsx`, and the pilot's own PostgreSQL data already contains `Assignment.status` rows at `ARRIVED`/`IN_PROGRESS`/`COMPLETED` from before this change; deleting the fields would have stranded that history with no migration path. `Assignment`'s ride-progress methods and fields therefore remain in the codebase, frozen (no longer written to by any production path) rather than deleted — a narrower, more conservative reading of "relocated to Trip" than this ADR's own text states. This ADR's own Decision-section wording is preserved below, unedited, per `CLAUDE.md`'s "Never Delete Documentation"; this note records where the actual implementation departed from it and why. Full record: `docs/PIOS_TAXI_TASK_12_TRIP_CONVERGENCE_REPORT.md`.

## Context

`docs/PIOS_TAXI_PRODUCT_DECISIONS.md` Section 9 (Product Owner-authority decision) ratifies the target domain split: **Order = passenger's request, Assignment = accepted operational commitment, Trip = actual service execution** — Trip must remain conceptually distinct from Assignment, and Trip is expected to live inside Dispatch's existing bounded context for Taxi V1, not as a new deployable service.

**Current implementation, traced directly from source:**

- `Order` (`backend/order-management/.../domain/Order.kt`) models exactly `SUBMITTED`/`COMPLETED`/`CANCELLED` — its own KDoc states directly that "the assigned, accepted, and ride states an order passes through once Dispatch allocates a driver... depend on Dispatch's own capability and remain outside this scope; they are not modeled here." This is unaffected by this ADR.
- `Assignment` (`backend/dispatch/.../domain/Assignment.kt`) currently models **both** the match decision and the ride-in-progress facts in one aggregate: `AssignmentStatus` is `CREATED, ACCEPTED, ARRIVED, IN_PROGRESS, COMPLETED`. The class's own KDoc for `arrivedAt`/`startedAt`/`completedAt` cites `ADR-043` (Owner Control Center — Observation Boundary) — a document about *operational observability*, not about the match decision — as their justification, independent evidence that these three facts already sit at a different conceptual layer than `accept()`'s own match-decision timestamp.
- Corresponding events, modeled in Dispatch's domain layer: `OrderAssigned` (produced by `Assignment.create()`, actually published by both real production Assignment-creation paths — Task 11A, confirmed), `AssignmentAccepted` (produced only by `Assignment.accept()`, which — per Task 11A's own call-graph verification — is not reachable from any controller and is therefore **not currently published in production**, despite `INTERFACE_CONTRACTS.md` Section 5's own text describing it as consumed by Order Management), and `AssignmentArrived`, `AssignmentStarted`, `AssignmentCompleted` (ride-progress; `AssignmentCompleted` alone is consumed by Order Management, per `ADR-041` Decision item 1, "the single trigger that completes an Order"; `AssignmentArrived`/`AssignmentStarted` are deliberately unconsumed by any module, per `ADR-041` Decision item 4).
- No `Trip` concept, table, class, or event exists anywhere in the repository today (confirmed by direct search — no `Trip.kt`, no `trips` table).

## Problem

Should the ride-progress facts (`ARRIVED`, `IN_PROGRESS`, `COMPLETED`) currently modeled on `Assignment` be split into their own aggregate, and if so, where does it live?

## Decision

**Yes — a new `Trip` aggregate is authorized, owned by Dispatch, living inside Dispatch's existing module (not a new deployable service).**

**Boundary, stated explicitly:**
- **Assignment** retains exactly the match decision — `AssignmentStatus` narrows to `CREATED`, `ACCEPTED` (and, unaffected by this ADR, whatever future `DECLINED`/cancellation states a separate decision might add — not addressed here). `Assignment.accept()` remains unchanged; `Assignment.arrive()`/`start()`/`complete()` are removed from `Assignment` and relocated to `Trip`.
- **Trip's creation trigger is `OrderAssigned` (corrected, Task 11A) — historical record of the two prior attempts at this bullet preserved below, per `CLAUDE.md`'s "Never Delete Documentation."**

  **Attempt 1 (this ADR's original text): "the moment `Assignment.status == ACCEPTED`."** Superseded — `ADR-040` Decision item 2 already documented that the one real path creating an Assignment today never separately calls `Assignment.accept()`, so this field is unreliable.

  **Attempt 2 (Task 10B's own correction): "the `AssignmentAccepted` event/outcome itself, never a read of `Assignment.status`."** Also superseded — Task 11's own mandatory pre-implementation call-graph inspection (not merely a field-level check, a constructor-level one) found that `AssignmentAccepted` is itself never produced by any live production path either: it is constructed only inside `Assignment.accept()`, which is called only by `DispatchAssignmentApplicationService.acceptAssignment()`, which no controller invokes. Attempt 2 correctly rejected the *field* but incorrectly assumed the *event* was still reliably produced by the same path whose field it had just shown was unreliable — it was not.

  **Attempt 3, current (Task 11A): `OrderAssigned`.** Both real production paths that create an Assignment (`ProposalAssignmentOrchestrationService.acceptProposal` on Proposal acceptance, and `AssignmentController.assignOrder` on Coordinator manual assignment) call `Assignment.create()`, which reliably, unconditionally publishes `OrderAssigned` — confirmed by direct reading of both call sites, not inferred. This is now the authoritative Trip creation trigger: **`OrderAssigned → Trip.create()`**, in-process, within the same module, not a new cross-module event (unchanged reasoning from the prior attempts on this point — Trip's creation remains entirely Dispatch-internal regardless of which of Dispatch's own already-published events triggers it). **Trip creation does not mean the passenger's ride has started** — `OrderAssigned` fires at the moment a driver is connected to an order, before any ride-progress fact exists; `Trip` begins in its own initial, pre-ride-progress lifecycle state (see `TripStatus` below), distinct from `ARRIVED`.

  `TripStatus`: `ARRIVED`, `IN_PROGRESS`, `COMPLETED` (renamed 1:1 from today's `AssignmentStatus` values of the same name, per the product decision's own "must not collapse" instruction — no ride-progress state is added, removed, or redefined by this ADR, only relocated) — plus, per Task 11A's own requirement that Trip "begin in its correct initial pre-ride lifecycle state," an initial state preceding `ARRIVED` (its exact name is an implementation detail for the next implementation task, not decided here — e.g. `CREATED`, mirroring `AssignmentStatus`'s own existing initial-state naming convention).
- **Trip's own events**: `TripArrived`, `TripStarted`, `TripCompleted` — a rename of `AssignmentArrived`/`AssignmentStarted`/`AssignmentCompleted`, same meaning, same publisher module (Dispatch), same consumer relationship (`TripCompleted` consumed by Order Management exactly where `AssignmentCompleted` is today; `TripArrived`/`TripStarted` remain unconsumed by any module, exactly as `ADR-041` Decision item 4 already established for their predecessors).
- **Order** is entirely unaffected — it already excludes ride-progress states by design; nothing about this ADR touches `Order.kt`, its migrations, or its own event contract.

**Why Dispatch, not a new deployable module** (this task's own instruction, "not a new deployable service," ratified as a constraint, evaluated here against `MODULE_STRUCTURE.md`'s own Extension Strategy, Section 8, which requires a new module only when a new bounded context is ratified through its own ADR): Trip's own data (driver, order references, three status timestamps) is a small extension of information Dispatch already owns and already timestamps (`Assignment.statusChangedAt`/`arrivedAt`/`startedAt`/`completedAt`, unchanged in substance, only relocated to a sibling aggregate). No new database, no new RabbitMQ topology, no new Windows service, no new INTERFACE_CONTRACTS.md provider is required — only a new table and a new aggregate class inside Dispatch's own already-provisioned `pios_dispatch` database and already-running service. Splitting Trip into its own deployable module today would be exactly the kind of premature complexity `docs/PIOS_TAXI_V1_TARGET_ARCHITECTURE.md` Section 23 and `docs/PIOS_TAXI_ARCHITECTURE_CONVERGENCE_REVIEW.md` Section 2 already reasoned against, for a concept that is, at V1's actual scope, three status values and three timestamps.

**Relationship to other concepts, per this task's own required checks:**
- **Cancellation.** `Order.cancel()`/`ProposalWithdrawn` (`ADR-053`) already handle pre-acceptance cancellation; a mid-Trip cancellation is a distinct, not-yet-modeled case this ADR does not resolve — named as an open question (below), not silently assumed away.
- **Payment.** A future Payment context (not created by this ADR) would key off `TripCompleted`, exactly as `docs/PIOS_TAXI_V1_TARGET_ARCHITECTURE.md` Section 11 already specifies — unaffected by this ADR beyond confirming which event it should listen for once it exists.
- **Rating.** Same — a future Rating context keys off `TripCompleted`, unaffected beyond the same confirmation.
- **Repeat business.** Lives entirely outside the Order/Assignment/Trip triple, in Passenger Experience's Circle of Trust (`ADR-054`) — unaffected by how many Trip records accumulate for a given passenger/driver pair.
- **Future verticals.** The three-way ownership *pattern* (demand / match / execution, each a distinct aggregate) is intended to generalize; the *name* "Trip" is deliberately not genericized (e.g., not renamed "ServiceExecution") for a vertical that does not yet exist — a future vertical would define its own equivalent aggregate, in its own module, under its own name, following this same pattern, never sharing this `Trip` table.

## Constraints

- No new database, no new RabbitMQ vhost/exchange topology mechanism, no new Windows service — Trip lives entirely within Dispatch's existing infrastructure.
- No new cross-module dependency is introduced — Order Management's own consumption of ride-completion remains exactly one event, renamed, not multiplied or redirected elsewhere.
- No ride-progress state is added, removed, or redefined — this is a relocation, not a redesign, consistent with the product decision's own "do not collapse these concepts" instruction (which this ADR reads as also implying: do not silently expand them while separating them).
- This ADR does not itself rename or republish any event, create any migration, or write any code — it authorizes the target shape; implementation is a separate, future task.

## Consequences

- **`AssignmentArrived`/`AssignmentStarted`/`AssignmentCompleted` are the one genuine breaking-shape event change this whole decision chain has identified** (`docs/PIOS_TAXI_V1_TARGET_ARCHITECTURE.md` Section 24 already flagged this; reaffirmed, not newly discovered, by this ADR). Implementation must use a dual-publish migration window — both old and new event names published for one deprecation period — so Order Management's existing `AssignmentCompleted` consumer keeps working unmodified until it is deliberately updated to bind `TripCompleted` instead, per `ADR-010`'s own versioning discipline. **Not performed by this ADR.**
- `EVENT_CATALOG.md` Section 6 and `INTERFACE_CONTRACTS.md` Sections 5/7 will need updated entries once Trip is actually implemented — reflecting `TripArrived`/`TripStarted`/`TripCompleted` in place of their `Assignment*` predecessors, and noting the rename's own migration window. **Not performed by this ADR**, reserved for the implementation task.
- `ADR-040` (Assignment Ride Lifecycle) and `ADR-041` (Order Lifecycle Synchronization with Assignment Completion) are **not superseded** — their own decisions (that ride-progress states exist, and that `AssignmentCompleted`/its successor is Order's own single completion trigger) remain exactly as ratified; only the aggregate *name* and *location* of the states they describe changes. A future documentation pass should add a cross-reference from both to this ADR, not rewrite either.
- Dispatch's own database gains one new table (`trips`) and Dispatch's own domain layer gains one new aggregate class — both additive, no existing table or class is dropped by this decision alone (the relocation itself, when implemented, will need its own migration plan, not designed here).
- **Implementation note, not a design decision (corrected, Task 11A)**: the future implementation task should wire Trip's creation directly into both code paths that already produce `OrderAssigned` — `ProposalAssignmentOrchestrationService.acceptProposal` (Proposal acceptance) and `AssignmentController.assignOrder`'s own application-service path (Coordinator manual assignment), via `DispatchAssignmentApplicationService.handle`/`handleWithinCallerTransaction` — not into a read of `Assignment`'s own persisted status, and not into `Assignment.accept()`/`AssignmentAccepted` (Section below). Whether the pre-existing `ADR-040`-documented gap (`Assignment.accept()` never separately called, and — per Task 11A's own further finding — `AssignmentAccepted` therefore never published) is ever closed is a distinct question this ADR does not decide — Trip's own correctness does not require it.
- **Separate, pre-existing risk surfaced by Task 11A's own inspection, explicitly not fixed by this ADR or by Task 11A itself**: Order Management's `AssignmentAcceptedListener` is fully built, correctly wired, and bound to the `assignment.accepted` routing key — waiting for a message `AssignmentAccepted`'s own non-production means it will never receive. Independently, `OrderAssigned` — which *is* actually published on every real Assignment creation — has **no consumer at all** in Order Management, despite `INTERFACE_CONTRACTS.md` Section 7 listing it as a possible one. **Net effect: Order Management currently has no working event-driven signal that an order has been assigned to a driver, for any reason.** This is unrelated to Trip's own correctness (Trip's new `OrderAssigned` consumption is Dispatch-internal and does not depend on Order Management consuming anything) but is a real, separate integration gap, tracked here and in `docs/PIOS_TAXI_TASK_11A_ARCHITECTURE_CORRECTION.md` Section 7 — not addressed by this ADR, and explicitly not to be fixed as a side effect of implementing Trip.
