## 0. Метод

Часть утверждений ниже основана на прямом веб-поиске (не только на обучающих данных) — источники процитированы там, где это принципиально для точности (поддержка API браузерами, реальная приватность hash-based contact discovery). Часть — на прямом чтении текущей архитектуры PIOS в этой же сессии (`ARCHITECTURE_VERIFICATION_REPORT.md`, `docs/ADR/ADR-037-...md`, `docs/PIOS_PRODUCT_DECISIONS_NETWORK_RULES.md`). Где факт не удалось проверить (например, поддержка конкретной технологии российскими операторами), это указано явно как «требует проверки», не выдаётся за факт.

## 1. Что уже есть в PIOS сегодня — обязательная отправная точка

Прежде чем проектировать «с нуля», стоит честно сказать: PIOS **уже почти построил** значительную часть того, что здесь рекомендуется — просто не подключил.

- **Аутентификации нет вообще, нигде.** `CURRENT_DRIVER_ID = 'ILDAR001'` — жёстко закодированная константа во фронтенде (`frontend/src/pages/DriverHome/currentDriver.ts`); `Driver` в бэкенде — это `id`, `availability`, `displayName`, без какого-либо credential (`ARCHITECTURE_VERIFICATION_REPORT.md`).
- **`network-management` (порт 8085) уже реализует Person/Profile/Connection/Invitation** — полноценно, но полностью не вызывается никаким продакшн-кодом (тот же отчёт, Вопрос 2). Это ровно тот слой, о котором просит вопрос 5 этой задачи («User, Identity, Contact, Invitation, Relationship») — только он уже существует, дожидаясь ADR на реальную интеграцию (`ADR-037`, Consequences: «Future work connecting network-management's Connection concept to actual order routing... will need its own ADR»).
- **QR-приглашение уже реализовано** (эта же сессия, real QR через `qrcode`, не заглушка) — один из пунктов «современных возможностей», о которых спрашивает задача, уже не гипотеза, а рабочий код.
- **Происхождение связи и запрет модели владения клиентом уже утверждены как принцип** (`docs/PIOS_PRODUCT_DECISIONS_NETWORK_RULES.md`) — это прямо ограничивает то, какие модели контактной сети вообще допустимы (см. Вопрос 4 ниже).

Вывод, который стоит держать в голове на протяжении всего документа: **разрыв — не в отсутствующей архитектуре, а в отсутствующей идентичности, которая могла бы всё это связать.**

## 2. Вопрос 1 — Регистрация

| Способ | Плюсы | Минусы | Для PIOS |
|---|---|---|---|
| **Телефон + SMS OTP** | Универсально понятен; номер телефона = естественный ключ для поиска людей в контактах (см. Вопрос 4); не требует стороннего аккаунта | SMS не проходит регуляторную проверку AAL2 (NIST SP 800-63-4, июль 2025 — SMS OTP более не считается устойчивым к фишингу); стоимость $0.01–0.04 за отправку в США (порядок величины; для РФ/СНГ требует отдельной проверки тарифов); задержки доставки | **База идентичности, но не единственный механизм входа** — см. ниже |
| **WhatsApp** (Business API OTP) | Familiar UX в части рынков | Meta-инфраструктура, отдельная стоимость, нерелевантно для российского рынка, на который явно ориентирован текущий контент PIOS (`docs/PRODUCT_EXPERIMENT_NETWORK_PILOT_*`) | Низкий приоритет |
| **Telegram** (Login Widget / Telegram-based identity) | Уже даёт верифицированный номер телефона без своей SMS-инфраструктуры; в РФ/СНГ — доминирующий мессенджер, ранее уже фигурировал в контексте проекта (Telegram Bot упоминался в исходном обсуждении Driver Copilot) | Зависимость от стороннего сервиса вне юрисдикционного контроля PIOS; не решает проблему для тех, у кого нет Telegram | **Сильный кандидат именно для этого рынка** — стоит рассмотреть как основной или альтернативный путь верификации номера, не как замену телефону |
| **Apple Sign-In / Google Sign-In** | Готовая, бесплатная, знакомая пользователям инфраструктура | Не даёт номер телефона по умолчанию (Apple вообще может отдать relay-email вместо реального); слабо стыкуется с моделью «пригласи клиента по контакту» — OAuth-идентичность не匹match-ится с телефонной книгой | Полезно как **дополнительный**, не основной способ |
| **Passkeys / WebAuthn** | Формально не про «регистрацию», а про последующий вход — см. Вопрос 2 | Не решает задачу первичной верификации личности («это точно тот же человек, кому принадлежит этот номер?») | Не подходит как единственный механизм регистрации |
| **eSIM / привязка к устройству** | — | Это не реальный веб/PWA API — не существует стандартного способа для сайта или PWA прочитать eSIM-профиль устройства как идентификатор. Ближайший реальный аналог — Silent Network Authentication (ниже), а не eSIM как таковой. Стоит явно скорректировать формулировку задачи здесь — привязки к eSIM в вебе не существует. | Не применимо буквально |
| **Silent Network Authentication (SNA)** | Верифицирует владение номером через SIM-криптографию оператора за 1–4 секунды, без ввода кода; устойчиво к SIM-swap и фишингу (нет кода, который можно перехватить); по данным поставщиков — до 30% рост конверсии регистрации по сравнению с SMS | Требует мобильного интернета именно через оператора-партнёра; покрытие в США оценивается на уровне ~80% в 2026 (T-Mobile/AT&T/Verizon), но поддержка в России/СНГ **не проверена в рамках этого исследования — требует отдельного запроса к провайдерам (Twilio Verify SNA, Prelude, аналоги) о покрытии MTS/Beeline/MegaFon/Tele2**; цена выше SMS в 3–5 раз | Перспективно **как будущее улучшение** конкретно для рынков, где подтверждено покрытие — не как стартовое решение при неизвестном покрытии |

**Рекомендация для PIOS:** телефон как первичный, обязательный идентификатор (не как способ входа, а как *identity anchor* — то, что делает «Артур» разрешимым и в контактной книге, и в системе), с SMS OTP как стартовым механизмом верификации при первой регистрации, и явным местом для добавления Telegram-based верификации и/или SNA позже, без изменения самой модели идентичности (см. Раздел 4 — Identity как отдельная от Credential сущность именно ради этой замены).

Sources: [Silent Network Authentication: The Invisible Layer Replacing SMS OTP in 2026](https://securityboulevard.com/2026/04/silent-network-authentication-the-invisible-layer-replacing-sms-otp-in-2026/), [Verify Silent Network Auth Overview | Twilio](https://www.twilio.com/docs/verify/sna), [SMS OTP Alternative: Compare Authentication Methods for 2026](https://www.engagelab.com/blog/sms-otp-alternative)

## 3. Вопрос 2 — Вход (повторный, без паролей)

Здесь, в отличие от регистрации, **passkeys — однозначно правильный ответ**, а не один из вариантов:

- Нативная поддержка с iOS 16+, Android 9+, Windows 11, Chrome 108+, Safari 16+, Firefox 122+ — платформа уже почти везде.
- Синхронизация через экосистемы Apple/Google/Microsoft; кросс-платформенный сценарий (например, iPhone → вход на чужом Windows-компьютере) — через QR-код, тот же паттерн, что PIOS уже использует для приглашений.
- По данным FIDO Alliance: 93% успешных попыток входа против 63% у паролей, на 73% быстрее по времени.

**Рекомендация:** passkey как основной способ повторного входа на уже знакомом устройстве (создаётся сразу после первой SMS/Telegram-верификации, не отдельным шагом, который пользователь может пропустить); откат на повторную верификацию по телефону — только при входе с нового устройства без passkey.

Sources: [Authentication Trends in 2026: Passkeys, OAuth3, and WebAuthn](https://www.c-sharpcorner.com/article/authentication-trends-in-2026-passkeys-oauth3-and-webauthn/), [Passwordless Authentication in 2026: Complete Guide](https://guptadeepak.com/the-complete-guide-to-passwordless-authentication-in-2026-how-it-works-why-it-matters-and-how-to-implement-it/)

## 4. Вопрос 3 — Доступ к телефонной книге

Прямой, проверенный поиском ответ, без сглаживания:

| Платформа | Возможность | Детали |
|---|---|---|
| **Android, Chrome** | Да | Contact Picker API доступен по умолчанию с Chrome 80+ на Android. |
| **Android, PWA (установленное веб-приложение)** | Да | Работает так же, как в браузере — Chromium-движок общий. |
| **iOS, Safari (браузер)** | **Нет по умолчанию** | Требует ручного включения экспериментального флага пользователем (Settings → Safari → Advanced → Feature Flags) — не то, на что можно рассчитывать в продукте. |
| **iOS, PWA** | **Нет** | WebKit (единственный разрешённый движок на iOS) не поддерживает Contact Picker API даже в установленном PWA. |
| **Полноценное нативное приложение (Swift, не веб)** | Да, полностью | Через нативный Contacts framework — но это уже не PWA, а отдельная разработка. |

**Важная деталь модели, которую стоит подчеркнуть отдельно:** даже там, где API доступен (Android), это **не «дай мне всю адресную книгу»** — это `navigator.contacts.select()`, разовый пикер, где пользователь сам выбирает конкретные контакты для конкретного действия, каждый раз заново, по явному действию пользователя. Никакого фонового/постоянного доступа не существует ни на одной платформе через веб.

**Обходное решение для iOS**, честно: его не существует на уровне PWA. Единственные реальные пути — (а) ручной ввод/выбор через `<input type="tel">` с автозаполнением из системной адресной книги iOS (это работает везде, в т.ч. на iOS — но это автозаполнение одного поля, не массовый выбор), либо (б) отложить массовый импорт контактов до полноценного нативного приложения (см. Раздел 8, «что отложить»).

Sources: [A contact picker for the web | Chrome for Developers](https://developer.chrome.com/docs/capabilities/web-apis/contact-picker), [Contact Picker API - Web APIs | MDN](https://developer.mozilla.org/en-US/docs/Web/API/Contact_Picker_API), [PWA iOS Limitations and Safari Support [2026]](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)

## 5. Вопрос 4 — Клиентская сеть (отдельно отмечен как приоритетный)

Здесь стоит прямо предостеречь от самой очевидной идеи — «сделать как WhatsApp»:

**Почему НЕ копировать модель WhatsApp/Telegram (загрузка контактов + хэш-сопоставление).** Поиском подтверждено: наивное хэширование телефонных номеров (даже усечённый SHA-256, как исторически делал Signal) **не даёт реальной приватности** — пространство телефонных номеров достаточно мало, чтобы переборщить весь мировой диапазон менее чем за 150 секунд на потребительской видеокарте (задокументированное академическое исследование, не гипотеза). WhatsApp и Telegram в принципе не хэшируют — загружают контакты на сервер как есть. Signal вложил серьёзные ресурсы в secure-enclave-based Private Contact Discovery именно потому, что простое хэширование оказалось сломано. Строить такую же серверную инфраструктуру ради контактной сети такси-платформы — явно несоразмерные затраты и риск.

**Что реально нужно PIOS — и что технически проще, не сложнее.** PIOS не пытается ответить на вопрос «кто из ВСЕХ моих контактов уже в PIOS» (это и есть тот самый дорогой, рискованный bulk discovery). PIOS отвечает на другой, гораздо более узкий и уже архитектурно предрешённый вопрос: **«кого из своих клиентов я хочу пригласить прямо сейчас»** — это уже прямо соответствует уже утверждённому принципу происхождения связи (`docs/PIOS_PRODUCT_DECISIONS_NETWORK_RULES.md`, Принцип 1: «Первый пригласивший получает признание за создание связи» — связь всегда явная, атрибутируемая, инициированная конкретным действием, никогда не пассивным сканированием). Это ровно то, для чего Contact Picker API создан: пользователь сам выбирает один или несколько контактов из системного пикера, ничего не загружается на сервер массово, каждый выбор — явное действие. Приватность здесь не требует криптографии — она следует из самой формы взаимодействия.

**Практическая схема:**
1. Водитель нажимает «Пригласить из контактов» (Android/Chrome — реально сегодня; iOS — недоступно, см. Вопрос 3).
2. Открывается системный пикер, водитель выбирает одного/нескольких клиентов.
3. Для каждого выбранного контакта PIOS формирует персональную ссылку-приглашение (уже реализовано) и передаёт управление системному Share Sheet — водитель отправляет её через SMS/WhatsApp/Telegram, куда угодно, как обычно.
4. Ничего из адресной книги никогда не попадает на сервер PIOS — только то, что происходит после: явный факт «эта ссылка была открыта», уже привязанный к конкретному коду приглашения (текущий, уже описанный в `PIOS_PRODUCT_DECISIONS_NETWORK_RULES.md`, механизм происхождения связи).

Это не откладывает «современный способ» — это и есть современный способ, при этом более простой и более приватный, чем то, что делают крупные мессенджеры.

## 6. Вопрос 5 — Модель пользователей

Предложение, построенное поверх уже существующего, не взамен:

```
Identity  (новое)
  — телефон как identity anchor; НЕ путать с Credential
  — одна Identity может подтверждаться разными Credential
        |
        v
Credential  (новое)
  — Passkey | SMS-verified session | (позже) SNA | (позже) Telegram-verified
  — множественная: у одной Identity может быть несколько устройств/passkey
        |
        v
Person  (уже существует, network-management, сегодня не используется)
  — то, что ADR-037 уже описал: "not a merger of Driver and Passenger;
    a new, independent identity concept"
  — теперь имеет ровно одно основание: Identity
        |
        +--> Profile: DRIVER  --> ссылка на Driver Management (по id, не по владению)
        +--> Profile: PASSENGER --> ссылка на Passenger Experience (по id, не по владению)
        |
        v
Connection / Invitation  (уже существует, network-management)
  — без изменений в форме; меняется только то, что теперь способ
    создания связи может быть Contact Picker, а не только ссылка
```

**Главный архитектурный вывод, ради которого стоило проводить это исследование:** ничего из «Device», «Contact» как отдельной постоянной сущности **создавать не нужно**. Device — это просто Credential (passkey привязан к устройству по своей природе, отдельная таблица не нужна). Contact — это не сущность, которую PIOS хранит, а **эфемерный результат одного вызова Contact Picker API**, который тут же превращается в конкретное Invitation — самостоятельного постоянного «Contact» не появляется нигде, и не должно.

**Единственная новая архитектурная граница:** `Identity`/`Credential` — это, скорее всего, **новый bounded context**, не расширение существующего — ни `driver-management`, ни `passenger-experience`, ни `network-management` сегодня не владеют понятием подтверждённого владения телефонным номером. По аналогии с тем, как `network-management` сам получил ADR-037, этому потребуется собственный ADR, расширяющий `ADR-017`/`ADR-018` (девятый контекст уже есть — это был бы десятый).

## 7. Вопрос 6 — Масштабирование до 100 000 / 1 000 000

Что уже готово к масштабу без переделки — не гипотеза, а прямое следствие уже принятых решений:

- Каждый модуль — своя PostgreSQL база, независимо деплоится (`ADR-023`, `ADR-026`) — добавление `identity`-модуля с собственной БД ничего не меняет в этой модели, только добавляет девятую (десятую) базу.
- Событийная архитектура (`ADR-003`) уже рассчитана на то, что новый модуль подписывается на события, не встраивается в существующий код — `IdentityVerified`/`CredentialRegistered` естественно ложится в уже существующий паттерн.

Что реально требует внимания именно при росте:

- **Стоимость SMS OTP линейно растёт с числом регистраций** — при 100 000 пользователей это уже заметная статья расходов ($0.01–0.04 × число попыток, не только успешных); passkey как способ входа снимает нагрузку с повторных входов, но не с первичной регистрации.
- **Нагрузка на Contact Picker-based приглашения не масштабируется на сервере вообще** — вся работа происходит на устройстве пользователя, сервер видит только результат (Invitation) — это архитектурно уже «бесплатно» с точки зрения роста.
- **Единая точка отказа, которую стоит явно зафиксировать заранее:** если Identity станет отдельным модулем, через который проходит подтверждение личности для входа в любую роль (Driver или Passenger), это неизбежно самый критичный по доступности модуль в системе — стоит спроектировать с расчётом на это с первого дня, не как последующую оптимизацию.

## 8. Вопрос 7 — Безопасность без паролей

- **Подтверждение личности:** SMS OTP (или Telegram/SNA) при первой регистрации — единственный момент, когда действительно проверяется «этот номер у этого человека»; всё последующее (passkey) подтверждает не личность, а «то же устройство/тот же passkey, что был выпущен этой Identity».
- **Защита аккаунта:** passkey сам по себе устойчив к фишингу (в отличие от SMS-кода, который можно выманить) — это не дополнительная мера, а свойство самого механизма.
- **Восстановление доступа:** при потере всех устройств — единственный путь назад **обязан** быть тем же каналом, что при регистрации (повторная SMS/Telegram-верификация того же номера), не «секретный вопрос» и не email (никакой email не собирается по всей текущей модели PIOS).
- **Смена телефона:** это ровно причина, по которой Identity и Credential должны быть разделены (Раздел 6) — новый номер верифицируется заново, новый passkey выпускается, но `Person`/история/связи в `network-management` не создаются заново — тот же Identity, обновлённый anchor.
- **Вход на новом устройстве:** тот же поток, что описан в Разделе 3 — QR-based кросс-девайсный passkey flow, откат на SMS/Telegram при отсутствии passkey.

## 9. Вопрос 8 — Возможности, которые могли быть не учтены

- **QR-приглашение** — уже реализовано в этой сессии, не гипотеза.
- **Universal Links / App Links** — актуальны только когда появится устанавливаемое приложение (не PWA) — тогда `/i/{code}` открывается сразу в приложении, не в браузере; сегодня преждевременно.
- **Digital Wallet passes (Apple Wallet / Google Wallet)** — реалистичная идея для *водителя*: цифровая визитка/пропуск с QR, которую можно добавить в Wallet и предъявлять физически (актуально для сценария «водитель уже физически рядом с клиентом» — сильнее, чем ссылка, для оффлайн-контакта). Не исследовано технически подробно здесь — кандидат для отдельного, более узкого исследования, если понравится направление.
- **Web NFC** — теоретически позволил бы «приложить телефон к телефону» для передачи ссылки — доступен только в Chrome на Android, та же асимметрия платформ, что и Contact Picker; не рекомендуется как основной канал по той же причине.
- **Contact Picker API** — уже разобран выше как основной ответ на Вопрос 4, не отдельная «дополнительная» идея.

## 10. Итоговый отчёт

**1. Анализ современных решений** — см. Разделы 2–5 и 9 выше; ключевой, не самый очевидный вывод — контакт-дискавери в духе WhatsApp криптографически несостоятелен, и PIOS не нужен такой механизм в принципе, поскольку модель явного, атрибутируемого приглашения (уже утверждённая) решает задачу проще и безопаснее.

**2. Рекомендуемая архитектура именно для PIOS** — Identity/Credential как новый, десятый bounded context, поверх уже существующего, не вместо него; `Person`/`Connection`/`Invitation` в `network-management` остаются как есть, только получают основание (Identity), которого у них сегодня нет. Полная схема — Раздел 6.

**3. Что можно реализовать уже сейчас** (в рамках PWA, без нового ADR на архитектуру идентичности — уже реализуемо только UI/UX-слоем, аналогично прошлым проходам этой сессии): ничего из перечисленного не входит в эту оговорку буквально, поскольку Identity как таковая — уже архитектурное изменение, требующее ADR. Что технически готово хоть сегодня без ADR: Contact Picker для Android (расширяет, не заменяет, уже существующий механизм «поделиться ссылкой» — тот же самый invitationLinkFor, только источник контакта меняется с ручного набора на пикер).

**4. Что лучше отложить до полноценного мобильного приложения:** массовый импорт контактов на iOS (архитектурно невозможен в PWA — не вопрос приоритета, а платформенное ограничение), Universal Links/App Links, Web NFC, физические Wallet-визитки.

**5. Какие технологии наиболее перспективны:** Passkeys/WebAuthn — не «перспективны», а уже зрелая, рекомендуемая к внедрению технология для входа (не для первичной регистрации). Contact Picker API — перспективен только на Android; для iOS перспектива лежит не в вебе, а в решении о нативном приложении. Silent Network Authentication — перспективен условно, до проверки покрытия российских операторов.

**6. Что я рекомендую изменить в текущей архитектуре PIOS до начала массового использования:**
- Добавить Identity/Credential как отдельный bounded context — не расширять `driver-management`/`passenger-experience` каждый по отдельности собственной, дублирующей логикой идентичности.
- **Не откладывать** это до «после пилота» бесконечно — сегодняшняя модель (`CURRENT_DRIVER_ID` как жёстко закодированная константа) физически не переживёт больше одного реального водителя одновременно; это не polish-задача, это блокер даже для второго участника пилота, если пилот вообще должен когда-либо выйти за пределы одного человека.
- Не строить контакт-дискавери по образцу мессенджеров — явно зафиксировать (например, отдельным Product Decision по аналогии с уже существующими в `docs/`) принцип «только явный выбор через пикер, никогда — фоновое сопоставление адресной книги» до того, как кто-либо предложит «а давайте как в WhatsApp» на будущем спринте.
