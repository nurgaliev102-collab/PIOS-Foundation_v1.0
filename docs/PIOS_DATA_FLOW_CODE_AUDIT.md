**Статус: факты, извлечённые из кода. Не решение, не ADR, не юридическое заключение.** Составлен по прямому запросу продукт-овнера (2026-09-07) — доказать по коду фактическую модель обработки данных, а не рассуждать о праве. ## 0. Как это читать

- «Reader» / «Writer» — что реально проверяет код (кто технически может прочитать/изменить), не что «должно быть».
- «PIOS own purpose?» / «Business purpose?» — не взаимоисключающие: один поток данных может обслуживать обе цели одновременно, это указано явно.
- Всё, помеченное **[НЕ НАЙДЕНО]** — проверено поиском по всему `backend/` и `frontend/src/`, реально отсутствует в коде на сегодня, не «пока не посмотрел».

## 2. Connection — глубже, как просили

**Категория A (Business Relationship: водитель/бизнес → его клиент)** — это `passenger-experience/domain/Connection.kt`. Факты:
- Единственные поля — голые идентификаторы (`driverId`, `passengerReference`), никаких имён/телефонов.
- Собственный комментарий в коде прямо называет цель: дать этому конкретному водителю приоритет на новый заказ от этого конкретного пассажира («First Refusal»).
- Доступ водителя к этим данным сознательно урезан — он не видит даже `isPrimary`, только сам факт связи и дату.
- Это единственная реально работающая, живая версия «Connection» в системе сегодня.

**Категория B (PIOS Network Relationship: связь для собственного matching/discovery/marketplace/рекомендаций PIOS)** — код такой активной сущности сегодня **не содержит**. `network-management/domain/Connection.kt` структурно мог бы стать такой сущностью, но по собственному комментарию кода («not read by Dispatch, Order Management, or any order-routing decision») и по независимому подтверждению — ни один реальный экран продукта её не вызывает (только внутренний тестовый харнес). Это не отсутствие возможности — это отсутствие активного использования. **Разница принципиальна**: и Category A, и (неактивная) Category B физически хранятся и управляются кодом PIOS — вопрос «кто фактически определяет цель использования» не решается местом хранения. Для Category A цель, вписанная в сам код — польза конкретного водителя. Для (неактивной) Category B никакой цели в коде не вписано вообще, потому что она не используется.

**Прямой вывод из кода: сегодня PIOS не отправляет во внешний AI ничего из перечисленного списка, ни при каких обстоятельствах.** Единственный существующий AI-поток (AI-советник владельца) структурно ограничен только числами. Служба поддержки с AI (обсуждавшаяся ранее) — не построена, значит открытый вопрос про «весь текст пользователя во внешний AI» относится к будущему коду, не к существующему.

**Отдельно важный факт для будущего сравнения провайдеров**: `OllamaProvider.kt` — локально размещаемая модель (`pios.ai-advisor.provider=ollama`), без обязательного API-ключа для обычного локального случая (`OllamaProvider.kt:33-38`). Если PIOS когда-либо использует именно этот провайдер, размещённый на своём же сервере — это единственный из трёх вариантов (DeepSeek/Qwen — оба зарубежные облачные API), который технически не создаёт трансграничную передачу вообще, потому что данные никуда не покидают собственную инфраструктуру PIOS.

## 4. Юридическая архитектура, которую поддерживает текущий код (не заключение)

Вопрос продукт-овнера: можно ли реально построить PIOS как B2B SaaS, где PIOS — оператор своих платформенных данных, бизнес (водитель) — оператор своей клиентской базы, PIOS обрабатывает её по поручению, и отдельно PIOS — оператор собственных Network-функций. Ниже — только то, что код фактически подтверждает или чему противоречит, без вывода.

### Что код ПОДДЕРЖИВАЕТ

- **Модульная изоляция без общего хранилища данных реальна, не декларативна.** Каждый факт (Identity/phone, Driver/displayName, Order/passengerName, Connection) физически лежит в своей базе, пересекается только голыми строковыми идентификаторами (подтверждено во всех прочитанных файлах — `OrderReference`, `DriverReference`, `PassengerReference` — все `value class`, содержащие только `String`, ничего больше). PIOS структурно не может сегодня собрать «единый профиль человека» одним запросом ни в одной базе.
- **Circle of Trust (Категория A) в самом коде обосновывается пользой конкретного водителя, а не платформы** — это не интерпретация, это буквальный текст комментария в `Connection.kt`. Урезанный доступ водителя (без `isPrimary`) — тоже поддерживает мысль «эти данные обслуживают отношения, а не платформенный профиль».
- **AI-советник (единственный живой AI-поток) архитектурно исключает personal data по конструкции**, не по обещанию — тип данных, которые физически можно передать, не содержит полей для имени/телефона/адреса ни при каких значениях.
- **Network Management структурно изолирован и неактивен** — то есть сегодня у PIOS буквально нет действующей функции «PIOS как оператор собственной сети для matching/discovery», которую нужно было бы отдельно классифицировать — вопрос пока чисто гипотетический на уровне кода.

### Что код ПРОТИВОРЕЧИТ / ослабляет эту модель

- **`POST /v1/orders` (создание заказа) не требует авторизации вообще** — `passengerName`, `pickupAddress` может отправить кто угодно, без привязки к аутентифицированному аккаунту в момент создания. Для чистой модели «оператор ↔ обработчик» обычно ожидается прослеживаемая, аутентифицированная цепочка получения данных — здесь её на входе нет.
- **`GET /v1/proposals?orderId=` намеренно оставлен без авторизации** (осознанное решение, не забытое) — хотя сам по себе не раскрывает имя/телефон, раскрывает связку заказ↔водитель без проверки, кто спрашивает.
- **Создание Proposal (`POST /v1/proposals`) не проверяет, что вызывающий — реальный владелец заказа** — известный, зафиксированный в самом коде пробел.
- Для Order данных нет чистого разделения «эта часть — для платформы, эта — для конкретного водителя»: `passengerName`/`pickupAddress` хранятся в базе Order Management (принадлежащей платформе технически), но по смыслу — это детали конкретной сделки между конкретным водителем и конкретным пассажиром, не платформенная функция сама по себе. Код не проводит эту границу нигде — она полностью размышление, не структура.
