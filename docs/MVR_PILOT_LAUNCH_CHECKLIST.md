# PIOS — Чек-лист запуска пилота v1.0

Status: Draft — Product Owner-authority document (`PROJECT_CONSTITUTION.md` Section 7), Sprint 5 (Pilot Launch Preparation). Операционный чек-лист, не архитектурный документ — предназначен координатору/оператору пилота на день подготовки и день запуска.

Derived from `MVR_PILOT_OPERATION_PLAN.md` (Section 4.1, расширено) и `MVR_COORDINATOR_GUIDE.md` (Sections 2, 7). Не меняет критерии успеха или ограничения, зафиксированные в этих документах — только организует их в последовательность действий.

---

## До первого дня

- [ ] Выбраны 3–5 водителей для пилота.
- [ ] Каждому водителю создан аккаунт (технический шаг, `MVR_COORDINATOR_GUIDE.md` Section 3) — водитель существует и виден в списке водителей координатора.
- [ ] Каждому водителю подготовлена личная ссылка/QR — открыта и проверена лично каждым водителем до дня запуска.
- [ ] Приложение доступно с телефона — открыто и проверено с реального телефона, не только с рабочего компьютера (`MVR_PILOT_OPERATION_PLAN.md` Section 3, сетевой доступ).
- [ ] Базы данных всех трёх нужных модулей на актуальной версии (Driver Management, Order Management — через V6, Dispatch — через V4); все три сервиса запущены и отвечают.
- [ ] Создание заказа проверено технически (тестовый заказ дошёл до Order Management).
- [ ] Проведён один полный тестовый цикл целиком: заказ → предложение → принятие → подтверждение — без участия реального водителя или пассажира, силами команды.
- [ ] Журнал ошибок и форма обратной связи готовы и доступны координатору (`MVR_PILOT_FEEDBACK_TEMPLATE.md`).

## День запуска

**Кто отвечает за что** — заполняется перед стартом, конкретными именами (не ролями):

| Роль | Кто отвечает |
|---|---|
| Координатор (ведёт цикл, отправляет предложения) | __________ |
| Кто звонит водителю при отсутствии ответа | __________ |
| Кто помогает пассажиру при затруднении | обычно сам водитель, пригласивший этого пассажира; координатор — только если водитель сам не может помочь |
| Где фиксируются ошибки по ходу дня | `MVR_PILOT_FEEDBACK_TEMPLATE.md`, Раздел 1, заполняется координатором сразу по факту, не в конце дня |

Правило дня запуска: любая неожиданность записывается сразу, а не по памяти вечером — координатор держит форму обратной связи открытой рядом с экраном координатора весь день.

## После запуска

- [ ] Собраны формы обратной связи по каждой попытке (`MVR_PILOT_FEEDBACK_TEMPLATE.md`, Разделы 2–4 — от водителя, пассажира, координатора).
- [ ] Каждое отдельное наблюдение классифицировано: Bug / Friction / Feature request / Product signal (`MVR_PILOT_FEEDBACK_TEMPLATE.md`, Раздел 5).
- [ ] Отдельно выделены все `Product signal` — они не решаются кодом, читаются в контексте главного вопроса пилота (`MVR_PILOT_FEEDBACK_TEMPLATE.md`, Раздел 6), а не как список задач для разработки.
- [ ] Только после этого — не раньше — обсуждается, какие `Bug` действительно требуют исправления сейчас, а какие `Friction`/`Feature request` могут подождать следующего этапа.
