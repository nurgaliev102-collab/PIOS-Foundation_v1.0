# PIOS — Чек-лист запуска пилота v1.0

Status: Draft — Product Owner-authority document (`PROJECT_CONSTITUTION.md` Section 7), Sprint 5 (Pilot Launch Preparation). Операционный чек-лист, не архитектурный документ — предназначен координатору/оператору пилота на день подготовки и день запуска.

Derived from `MVR_PILOT_OPERATION_PLAN.md` (Section 4.1, расширено) и `MVR_COORDINATOR_GUIDE.md` (Sections 2, 7). Не меняет критерии успеха или ограничения, зафиксированные в этих документах — только организует их в последовательность действий.

---

## До первого дня

- [ ] Выбраны 3–5 водителей для пилота.
- [ ] Каждый водитель самостоятельно создал свой профиль в приложении (открывает приложение на своём телефоне, вводит своё имя — технической помощи не требуется, ADR-039) — водитель существует и виден в списке водителей координатора.
- [ ] Каждому водителю подготовлена личная ссылка/QR — открыта и проверена лично каждым водителем до дня запуска.
- [ ] Приложение доступно с телефона — открыто и проверено с реального телефона, не только с рабочего компьютера (`MVR_PILOT_OPERATION_PLAN.md` Section 3, сетевой доступ).
- [ ] Базы данных всех пяти нужных модулей на актуальной версии (Driver Management — через V3, Passenger Experience — через V1, Order Management — через V7, Dispatch — через V6, Identity — через V2); все пять сервисов запущены и отвечают. (`Network Management` в пилотный сценарий не входит — см. ADR-037.)
- [ ] Создание заказа проверено технически (тестовый заказ дошёл до Order Management).
- [ ] Проведён один полный тестовый цикл целиком: заказ → автоматическое предложение приглашающему водителю → принятие → «Прибыл» → «Поездка началась» → «Поездка завершена» — без участия реального водителя или пассажира, силами команды.
- [ ] Журнал ошибок и форма обратной связи готовы и доступны координатору (`MVR_PILOT_FEEDBACK_TEMPLATE.md`).

## День запуска

**Кто отвечает за что** — заполняется перед стартом, конкретными именами (не ролями):

| Роль | Кто отвечает |
|---|---|
| Координатор (следит за ходом пилота; предложение уходит автоматически приглашающему водителю при оформлении заказа — координатор вмешивается вручную только для нестандартных случаев, Раздел 4 `MVR_COORDINATOR_GUIDE.md`) | __________ |
| Кто звонит водителю при отсутствии ответа | __________ |
| Кто помогает пассажиру при затруднении | обычно сам водитель, пригласивший этого пассажира; координатор — только если водитель сам не может помочь |
| Где фиксируются ошибки по ходу дня | `MVR_PILOT_FEEDBACK_TEMPLATE.md`, Раздел 1, заполняется координатором сразу по факту, не в конце дня |

Правило дня запуска: любая неожиданность записывается сразу, а не по памяти вечером — координатор держит форму обратной связи открытой рядом с экраном координатора весь день.

## Сброс устройства между участниками

Между двумя разными пассажирами (или водителями), пробующими пилот на одном и том же телефоне/браузере, устройство нужно вернуть в состояние "первого запуска" — иначе новый участник увидит сохранённое имя и заказ предыдущего.

Самый простой и надёжный способ — **открыть приложение в новом приватном окне браузера** (Incognito/InPrivate) для каждого следующего участника и закрыть его после. Ничего очищать вручную не нужно.

Если приватное окно недоступно (например, тестируется установленное на телефон веб-приложение), очистите вручную следующие ключи в `localStorage` сайта (через DevTools → Application → Local Storage, либо `localStorage.clear()` в консоли, если на этом устройстве в этом браузере больше ничего важного не хранится):

- `pios.identity` — сохранённая личность водителя на этом устройстве (`frontend/src/identity/BackendIdentityProvider.ts`).
- `pios.passenger-identity` — сохранённое имя пассажира на этом устройстве (`frontend/src/persistence/localPassengerIdentity.ts`).
- `pios.current-order` — текущий незавершённый заказ пассажира на этом устройстве (`frontend/src/persistence/localCurrentOrder.ts`).

После очистки перезагрузите страницу — приложение должно снова показать экран приветствия/регистрации, как при первом заходе.

## После запуска

- [ ] Собраны формы обратной связи по каждой попытке (`MVR_PILOT_FEEDBACK_TEMPLATE.md`, Разделы 2–4 — от водителя, пассажира, координатора).
- [ ] Каждое отдельное наблюдение классифицировано: Bug / Friction / Feature request / Product signal (`MVR_PILOT_FEEDBACK_TEMPLATE.md`, Раздел 5).
- [ ] Отдельно выделены все `Product signal` — они не решаются кодом, читаются в контексте главного вопроса пилота (`MVR_PILOT_FEEDBACK_TEMPLATE.md`, Раздел 6), а не как список задач для разработки.
- [ ] Только после этого — не раньше — обсуждается, какие `Bug` действительно требуют исправления сейчас, а какие `Friction`/`Feature request` могут подождать следующего этапа.
