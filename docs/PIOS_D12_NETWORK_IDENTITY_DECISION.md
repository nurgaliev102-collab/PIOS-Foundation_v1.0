# PIOS D-12 — Network Person Ownership, Identity Mapping, and Authorization

## Status

**RATIFIED — IMPLEMENTED AND VERIFIED (Product Owner instruction, 2026-09-23).**

This decision authorizes only C-3 hardening of the dormant network-management
module: the local Person binding, authentication and object authorization of
its eight existing endpoints, migration, tests, and narrow append-only ADR
addenda. It does not authorize deployment, routing, production migration,
product activation, a new network-management caller, or changing Identity's
SMS/C-2 implementation. C-3 closure additionally requires verified tests and
build; ratification alone was not closure. The verification record in §13
completes that gate in this worktree without activating production.

## 1. Ratified decision

The Product Owner authorized implementation of this model:

1. `IdentityId` remains the authentication identity and the value of a signed
   session token's `sub` claim.
2. `PersonId` remains a separate, network-management-owned relationship
   identity generated by network-management.
3. A Person is owned by exactly one Identity through an immutable,
   one-to-one `persons.identity_id` reference stored only in
   network-management.
4. All eight network-management endpoints require a valid user Bearer token.
   There is no public, owner-Basic, or service-credential bypass.
5. The caller's Person is resolved server-side from the verified token's
   `sub`; request path/body/query identifiers never establish caller identity.
6. Both guest and registered Identity subjects may own a Person. Guest upgrade
   preserves `IdentityId`, so it preserves the Person binding without a
   migration or rebinding operation.
7. Existing Person rows are not automatically bound. They remain quarantined
   and unreachable through the protected API until a separately approved,
   evidence-backed reconciliation is available.
8. No participant phone number is returned through network-management. D-12
   does not reopen ADR-059.

Ratification of D-12 is deliberately narrower than activation of
network-management as a product capability. It authorizes the ownership model
needed to secure dormant endpoints; it does not authorize deployment, routing,
referral use, discovery, ranking, payment, trust, or any new caller.

## 2. Facts established by repository inspection

### 2.1 Identity and token semantics

- `Identity.id` is an `IdentityId` generated by Identity and persisted as
  `identities.id`, its primary key.
- Identity currently owns `phone`, optional `driver_id`,
  `phone_verified_at`, and `session_generation`.
- `SessionTokenIssuer` is the sole token issuer. A token contains at least
  `sub`, `drv`, `gst`, `sgen`, and `exp`; `sub` is the `IdentityId`.
- Other modules follow ADR-055 by verifying the HMAC token locally with a
  replicated `SessionTokenVerifier`. They do not call Identity per request.
- Guest upgrade is in-place: `UpgradeGuestIdentityApplicationService` keeps
  the same `IdentityId`. Phone recovery also keeps the same `IdentityId` and
  increments `session_generation`.
- ADR-082 explicitly accepts that non-Identity modules cannot compare `sgen`
  against the live Identity row. A pre-recovery token can therefore remain
  valid in those modules until `exp`. D-12 inherits that existing limitation;
  it does not introduce an Identity call or a new revocation architecture.

### 2.2 Network Person semantics

- `Person.id` is a network-management-generated `PersonId`, stored as the
  primary key of `persons`.
- A Person currently contains `name`, optional `phone`, and `created_at`.
- `PersonId` and `IdentityId` are intentionally different concepts. No column,
  table, event, or API currently maps one to the other.
- All eight network-management endpoints currently trust unauthenticated
  request data or have no caller identity at all.
- `PersonProfile`, `Connection`, and `Invitation` reference only `PersonId`.

### 2.3 Existing database constraints

- Identity enforces unique non-null phone and unique non-null `driver_id`.
- Network-management enforces primary keys and its internal Person foreign
  keys, but has no authentication-owner reference.
- The databases are separate. A cross-database foreign key is neither
  possible nor consistent with ADR-005/ADR-009 reference-not-ownership.

### 2.4 Existing authenticated inter-module patterns

- There is no service account, client-credentials, API-key, or mTLS identity
  mechanism for synchronous internal HTTP calls.
- `RestClientDriverOrderAccess` forwards the original user's Bearer token to
  Dispatch; Dispatch still authorizes the user represented by that token. This
  is delegated user authentication, not a service bypass.
- `OwnerCredentialGate` represents the platform operator, not a Person, and
  cannot establish object ownership for Person/Profile/Connection/Invitation.
- Consequently D-12 must not add owner-Basic or a fabricated service identity
  as an alternate path. Network-management can resolve ownership locally from
  `token.sub` once it stores the plain Identity reference.

## 3. Lifecycle: `IdentityId` ↔ `PersonId`

### 3.1 Creation

1. A client presents a valid Identity-issued Bearer token.
2. Network-management verifies the token locally and reads `sub` as the trusted
   `IdentityId`.
3. `POST /v1/persons` looks up `persons.identity_id = token.sub`.
4. If a row exists, creation is idempotent: return the existing Person with
   HTTP 200 and do not create another row.
5. If no row exists, network-management generates a new `PersonId` and inserts
   the Person with `identity_id = token.sub` and `identity_bound_at = now()` in
   one transaction; return HTTP 201.
6. A uniqueness race is resolved by the database unique index. The losing
   request reads and returns the already-created Person rather than generating
   a second owner record.

`PersonId` is never copied into Identity. Identity owns authentication;
network-management owns the relationship identity and the reference that lets
it authorize that identity's network objects.

### 3.2 Normal authenticated use

For every endpoint other than Person creation, network-management resolves:

```text
verified token.sub
        ↓
persons.identity_id
        ↓
callerPersonId (server-derived)
```

If the token is missing, malformed, expired, or fails signature validation,
the response is 401. If the token is valid but has no bound Person, the
response is 403 for every endpoint except `POST /v1/persons`.

Path/body/query Person identifiers remain resource selectors only. They never
become the caller identity. Where a self identifier remains in a path, it must
equal `callerPersonId`; where a body currently repeats caller identity, that
field is removed from the accepted contract. During any compatibility window,
a supplied legacy field must be compared with `callerPersonId`, rejected with
403 on mismatch, and never passed downstream as the trusted source.

### 3.3 Guest upgrade, driver association, and recovery

- Guest → registered upgrade: no mapping change because `IdentityId` is
  preserved.
- Driver association: no mapping change because only token `drv` and
  `identities.driver_id` change.
- Phone verification, or any future phone update that preserves the same
  Identity: no mapping change.
- Credential recovery: no mapping change because recovery preserves
  `IdentityId`; only credentials and `session_generation` change.
- Token refresh/login: no mapping change.

### 3.4 Rebinding and merge

There is no public rebinding endpoint. `persons.identity_id` is immutable after
creation. Name, phone, driver id, or possession of a Person id is never evidence
for rebinding.

If a user loses an unrecoverable guest Identity and later creates a different
Identity, the old Person is not transferred automatically. The new Identity
may create a new Person. Any future account merge or Person transfer requires a
separate decision defining proof, conflict handling, audit history, and the
effect on existing Profiles, Connections, and Invitations.

Identity deletion does not exist today. If introduced later, its effect on a
bound Person must be decided by that feature's ADR; D-12 does not infer cascade
or deletion across databases.

## 4. Exact storage model

Add one new, additive network-management migration. Do not modify an existing
migration and do not change the Identity schema.

```sql
ALTER TABLE persons ADD COLUMN identity_id TEXT;
ALTER TABLE persons ADD COLUMN identity_bound_at TIMESTAMPTZ;

ALTER TABLE persons
    ADD CONSTRAINT ck_persons_identity_binding_pair
    CHECK ((identity_id IS NULL) = (identity_bound_at IS NULL));

ALTER TABLE persons
    ADD CONSTRAINT ck_persons_identity_id_not_blank
    CHECK (identity_id IS NULL OR btrim(identity_id) <> '');

CREATE UNIQUE INDEX ux_persons_identity_id
    ON persons (identity_id)
    WHERE identity_id IS NOT NULL;
```

Semantics:

- `persons.id` remains the unique `PersonId` primary key.
- The partial unique index guarantees at most one Person per Identity.
- Each Person row has at most one Identity because `identity_id` is scalar.
- `identity_bound_at` records when ownership was established; the pair check
  prevents half-bound rows.
- `identity_id IS NULL` means a pre-D-12 legacy Person with no provable owner.
  New application writes must never create such a row.
- There is no cross-database foreign key and no synchronous existence check
  against Identity. A correctly signed token is the proof that the issuer
  minted that `sub`.
- The Person repository gains lookup by `identity_id`; the mapping is not
  exposed as a response field.
- Save/update SQL must never update `identity_id` or `identity_bound_at` after
  insertion. No API command accepts either field.

The columns are preferred over a general binding table because D-12 has one
immutable one-to-one association and no binding history, role, status, or
many-to-many lifecycle. A generic mapping abstraction would enable cases the
decision does not authorize.

## 5. Authorization definitions

### 5.1 Self-only

Self-only means the resource's owner is the Person resolved from the verified
`token.sub`. A valid token belonging to another Identity returns 403. Knowing a
Person id does not confer access.

Self-only applies to:

- creating or directly retrieving one's Person;
- creating or listing that Person's Profiles;
- creating Invitations as that Person;
- listing that Person's outgoing Connections.

### 5.2 Participant-scoped

Participant-scoped means the caller's server-derived Person must occupy the
specific participant position required by the operation:

- direct Connection creation: caller is always `fromPersonId`; only the target
  `toPersonId` and existing domain `type` remain client-selected data;
- Invitation acceptance: caller is always the accepting/to Person; the stored
  Invitation creator is the from Person;
- Connection listing: only the from/owner may list their outgoing connections.
  A target Person's display name may appear only because that target is in a
  stored Connection returned to the authorized source owner.

D-12 does not change existing Connection state or consent business rules. It
only establishes who may perform the existing action. Any decision to remove
direct `CONNECTED` creation, require target consent, or add inbound connection
reads is a separate product/domain decision.

No endpoint becomes public. A shareable Invitation code is not authentication;
accepting it still requires a valid user token and a bound caller Person.

For all eight endpoints, authentication is checked before parsing or looking up
request-supplied object identifiers. This preserves the required invariant that
an unauthenticated request is 401 rather than a validation-dependent 400/404.

Owner `Authorization: Basic` is not accepted. The owner credential proves an
operator, not a Person, and would bypass the D-12 ownership model. Any future
operator repair capability must be a separate, narrowly audited operation, not
an alternate branch on these participant endpoints.

## 7. Existing Person migration strategy

Existing rows have no trustworthy Identity owner. Neither `persons.phone`,
`persons.name`, Profiles, Connections, nor client knowledge of a `PersonId`
proves an Identity mapping. Automatic matching would conflict with ADR-038's
separation of authentication identity from relationship identity and could
transfer another person's network objects.

The safe migration is:

1. Add the nullable binding columns and constraints above. All existing rows
   remain `identity_id = NULL`, `identity_bound_at = NULL`.
2. Treat every null-bound Person, its Profiles, its outgoing Connections, and
   its Invitations as quarantined legacy data.
3. Do not return a quarantined Person through direct reads and do not accept it
   as a Connection target or Invitation creator through the protected API.
4. New authenticated callers create a new bound Person through the idempotent
   creation lifecycle. No name/phone heuristic links them to legacy rows.
5. Preserve legacy rows physically until a separate retention or reconciliation
   decision is made. D-12 authorizes neither deletion nor silent reassignment.
6. Produce a non-PII migration report containing counts and object ids only if
   reconciliation is later requested. Do not print phone values into migration
   logs or reports.
7. A later migration may make `identity_id` non-null only after every legacy
   row has been explicitly archived, deleted under authority, or mapped using a
   separately ratified proof process. D-12 does not claim that prerequisite is
   met.

This follows the ADR-055 precedent for historical passenger references: when
old data never proved an owner, a migration must not invent one.

## 8. Recovery and rebinding semantics

| Event | Mapping result |
| --- | --- |
| Guest upgraded in place | Unchanged; same `IdentityId` |
| Login on another device | Unchanged |
| Driver associated or changed in token | Unchanged; `drv` is not Person ownership |
| Phone verified or credential recovered | Unchanged; same `IdentityId` |
| `session_generation` incremented | Mapping unchanged; stale-token behavior remains ADR-082's accepted limitation outside Identity |
| Phone/name matches a legacy Person | No mapping; attributes are not proof |
| User presents a Person id from another account | 403; no rebinding |
| Identity A replaced by newly-created Identity B | No transfer; B may create a new Person |
| Future account merge | Not authorized; requires separate ADR and audited collision policy |
| Future Identity deletion | Not decided; no cross-database cascade is inferred |

There is no recovery path that changes `persons.identity_id`. Recovery restores
control of the same Identity. This keeps the mapping stable and prevents an
account-recovery endpoint from becoming a Person takeover endpoint.

## 9. Rejected alternatives

### 9.1 Make `PersonId == IdentityId`

Rejected. It collapses authentication identity and relationship identity,
contradicting ADR-038's explicit distinction and Person's existing
server-generated identifier semantics. It also offers no safe migration for
existing Person rows.

### 9.2 Store `person_id` in Identity

Rejected. ADR-038 states the intended direction: Person may reference Identity
once authorized. Storing the reverse reference makes Identity own a
network-management concern and requires Identity changes for a dormant module.
It also gives Identity no local way to enforce Person lifecycle integrity.

### 9.3 Match Person and Identity by phone

Rejected. `Person.phone` is an unverified relationship attribute; Identity
phone has authentication and verification semantics. ADR-038 explicitly says
they are different concepts, and ADR-059 forbids using network-management as a
contact-disclosure path. Phone equality is not proof of ownership.

### 9.4 Match by name, driver id, profile type, or existing connections

Rejected. These values are non-unique or express roles/relationships, not
authentication. Such inference can silently transfer another person's data and
violates deny-by-default object authorization.

### 9.5 Trust path/body/query Person ids after merely validating a token

Rejected. Authentication without binding does not prove ownership. It leaves
the original ID-substitution vulnerability intact and fails C-3's object-level
authorization requirement.

### 9.6 Add a new global authorization service or synchronous Identity lookup

Rejected. ADR-055 chose local token verification and replicated verifier code;
ADR-026/ADR-027 reject avoidable synchronous dependencies. The local plain
reference is sufficient and introduces no new runtime dependency.

### 9.7 Use owner Basic as a universal bypass

Rejected. Owner credentials authenticate an operator, not the Person who owns
the network object. A bypass would defeat self-only and participant semantics
and provide no server-derived `PersonId`.

### 9.8 Invent a service credential for network-management

Rejected. No such platform mechanism exists. Adding API keys, client
credentials, or mTLS is a platform-wide security decision, not a C-3
implementation detail. The known Bearer-forwarding pattern represents the
original user and does not solve ownerless background writes.

### 9.9 Put `IdentityId` directly into every Profile/Connection/Invitation

Rejected. It duplicates ownership references across aggregates and permits
them to drift. Existing domain references already converge on `PersonId`; the
single Person binding is the narrowest authorization seam.

### 9.10 Auto-delete legacy Person data

Rejected. Security quarantine does not imply authority to destroy data.
Deletion or archival needs an explicit retention decision.

### 9.11 Treat Invitation acceptance as public

Rejected. An Invitation code is shareable and therefore not a credential.
Public acceptance would recreate caller substitution and allow an anonymous
party to mutate both Invitation and Connection state.

## 10. ADR treatment after ratification

ADR-086 is an append-only addendum to ADR-037, ADR-038, ADR-064 and ADR-075
that records the specific D-12 exception. The original historical decisions remain in place;
where they conflict, the later dated D-12 addendum governs only this narrow
security-hardening scope. ADR-059 and ADR-055 are not changed.

### ADR-038 — implemented by ADR-086

ADR-086 states:

- the previously reserved Person↔Identity wiring is now authorized narrowly
  for network-management ownership and endpoint authorization;
- Identity and Person remain distinct aggregates and identifiers;
- network-management stores the plain `IdentityId` reference; Identity stores
  no `PersonId` and exposes no new lookup endpoint;
- `token.sub` is the only trusted authentication subject;
- guest upgrade and recovery preserve the mapping because they preserve
  `IdentityId`;
- no phone-based linking or disclosure is authorized.

This changes ADR-038's prior statement that the wiring is not authorized. It
does not merge the bounded contexts.

### ADR-064 — narrow supersession implemented by ADR-086

ADR-064 currently forbids any new work, read, write, or dependency involving
network-management and marks it superseded for product features. The update
must explicitly permit only:

- C-3 security hardening of the already-existing dormant module;
- the local `persons.identity_id` reference and local Bearer verification;
- migrations and tests necessary to enforce the ratified D-12 policy.

ADR-086 also preserves ADR-064's product placement decision:

- network-management is not selected for referral visibility, Circle of
  Trust, dispatch, discovery, or any current runtime feature;
- D-12 does not deploy or activate the module;
- any product caller or runtime dependency still requires a separate decision.

### ADR-059 — no decision change required

D-12 must reference ADR-059 and preserve its prohibition. `Person.phone` is
never returned and is never used to establish ownership. Any future phone
storage cleanup may be implemented separately, but no disclosure is authorized.

### ADR-075 — guest exception implemented by ADR-086

ADR-075 currently prohibits any guest read from or write to
network-management and any Identity↔Person linkage. Because ratified D-12
model allows a guest Identity to create a Person and relies on in-place guest
upgrade to preserve that binding. ADR-086 narrowly records that:

- permits a guest token to create and use only that guest's bound Person under
  the same D-12 self/participant rules;
- keeps the prohibition on every driver-side capability;
- does not make `gst` an authorization input in Dispatch, Order Management, or
  Passenger Experience;
- preserves the shorter guest-token TTL and the disclosed unrecoverable-guest
  risk.

### ADR-037 and ADR-055 — consistency notes

- ADR-037's zero-integration statement and its unresolved Identity/Person
  linkage require an append-only pointer to the ratified D-12 exception.
- ADR-055's token decision does not change. Documentation may add
  network-management to the inventory of local verifiers, but Identity remains
  the sole issuer and no per-request Identity call is introduced.

## 11. Ratified scope checklist

The Product Owner's 2026-09-23 implementation instruction accepts the
following D-12 scope for C-3:

- one Identity owns at most one Person and one Person has at most one Identity;
- mapping is stored in network-management and is immutable;
- guest identities may create and retain a Person through in-place upgrade;
- all eight endpoints are Bearer-only with no public/Basic/service bypass;
- the self-only and participant rules in the matrix;
- legacy rows remain unbound and inaccessible rather than heuristically mapped;
- there is no public rebinding or account-transfer path;
- ADR-059 remains unchanged and phone remains undisclosed;
- ADR-064 is superseded only for security hardening, not product activation;
- ADR-075 is superseded narrowly to allow a guest's own Person;
- ADR-082's existing non-Identity stale-token limitation is inherited.

## 12. Implementation and closure gate

The C-3 implementation consists of the additive `V2__identity_person_binding`
migration; a locally verified Identity token and one `CurrentPerson` resolver;
server-derived ownership on all eight existing routes; compatibility assertions
for legacy request identity fields; quarantine of null-bound historical rows;
API/negative security and PostgreSQL invariant tests. See the implementation
change set for the precise code and test files. `token.sub` is read only from
the verified server-side request context. The resolver looks up
`persons.identity_id`, returning the server-derived Person or 403. The client
cannot establish the caller by path/body/query Person identifiers.

No ordinary API may change `identity_id` or `identity_bound_at`. The unique
index and immutability trigger enforce this in PostgreSQL. Creation is
transactional and concurrent attempts converge on the same Person. Legacy
null-bound rows remain in storage and are excluded from authorized reads,
Connection targets, and Invitation creators. Identity deletion/disablement and
account merge are not existing operations; D-12 authorizes neither transfer
nor cascade. If introduced, they require a separate decision before use.

The module remains undeployed and unrouted. Configuration of the shared HMAC
secret and application of V2 in a future environment require a separately
authorized deployment. C-3 closure in this worktree means the code, tests,
build, and documentation gates pass; it is not production activation.
